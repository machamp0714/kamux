# kamux レーン起動

`docs/superpowers/plans/2026-08-01-kamux/` の実装フェーズを `lane-controller` エージェントとして起動する。
あなた（team-lead）はレーンを起動して監督するだけで、コードは書かない。

引数の形は 2 つ。

| 引数 | 動作 |
|---|---|
| `M1-1` 〜 `M3-4` | そのフェーズを 1 本だけ起動する |
| `stage0` 〜 `stage6` | そのステージのレーンを 1 メッセージ内でまとめて起動する（= 並列実行） |

引数が無い場合は、ledger（`.superpowers/sdd/*/progress.md`）と `git log` から現在地を推定し、次に来るステージを提案してから確認を取る。

## 章の書き方

契約は章を `§25` の形で書く。この定義ファイルの地の文では「25 章」と書くが、成果物（dispatch プロンプト・契約変更要求・報告・コミットメッセージ）へ書き込むときは `§25` の形を使う。
契約自身がその表記なので、章表記で書くと引く側の `grep` が当たらない。

## 1. 起動前チェック（毎回、必ず）

```bash
# 1. エージェント定義が認識されているか（5 種）
ls .claude/agents/

# 2. 作業ツリーが汚れていないか
git status --short

# 3. 直前のステージの成果がマージ済みか
git log --oneline -5

# 4. 起動・再開するフェーズの PR の終端状態と ledger の現在地を突き合わせる
#    ⚠️ --search "<フェーズ ID>" を使わない。GitHub の全文検索はハイフンを分解し body も走査するため、
#       無関係な PR が MERGED として返る（M3-4 で 8 本、うち M3-4 の PR は 0 本の実測）。title で絞る:
P=<フェーズ ID>
gh pr list --state all --limit 300 --json number,state,mergedAt,title \
  -q "[.[] | select(.title | test(\"(^|[^0-9A-Za-z])${P}([^0-9]|$)\"))] | \"件数=\(length)\", (.[] | \"\(.number)\t\(.state)\t\(.title)\")"
# 不合格の形: 件数=0、または返った title にフェーズ ID が含まれないこと
```

4 は再開のときほど効く。ledger は書き手が落ちると古いまま止まるが、PR の状態は GitHub 側に残る終端事実である。
ledger の完了行 9 行が実体 7 タスクで、完了・マージ済みのフェーズへレーンを 1 本起動した実例がある。完了行は行数ではなく distinct なタスク番号で数える。

`lane-controller` が利用可能エージェント一覧に出ていない場合はセッション再起動が必要。
フォールバックとして `subagent_type: "claude"` で起動し、`.claude/agents/lane-controller.md` の本文をプロンプト冒頭に貼る。

## 2. ステージの定義

依存グラフから導出済み（`TEAM.md` 1 章）。並列度は最大 3。クリティカルパスは 7 フェーズ直列なので、レーンを増やしても縮まない。

| ステージ | レーン | isolation | マージ順 | 備考 |
|---|---|---|---|---|
| stage0 | M1-1 | 不要 | — | 全フェーズをブロックする土台 |
| stage1 | M1-2 ∥ M1-3 | 両方 worktree | M1-2 → M1-3 | `App.tsx` / `store/index.ts` / `useKeymap.ts` / `package.json` が重衝突 |
| stage2 | M1-4 | 不要 | — | M1-1〜M1-3 すべてが前提 |
| stage3 | M2-1 ∥ M3-1 | 両方 worktree | M2-1 → M3-1 | 衝突は `main.rs` / `App.tsx` の追記のみ。M3-1 の前提は M1-3 だけなのでここに前倒し |
| stage4 | M2-2 ∥ M2-3 ∥ M3-2 | M2-2 / M2-3 のみ | M2-2 → M2-3 → M3-2 | M3-2 は純フロントで衝突ゼロ（隔離不要） |
| stage5 | M3-3 → M2-4 | 不要 | 直列 | 並列にしない。Rust/フロント両側で 10 ファイル衝突する |
| stage6 | M3-4 | 不要 | — | M1-1〜M3-3 すべてが前提 |

stage5 は 1 メッセージ 1 起動（直列）。M3-3 の完了を待ってから M2-4 を起動する。

isolation 列が「worktree」の行は、`isolation: "worktree"` ではなく `git worktree add` で手動作成する。
ハーネスの隔離 worktree は自動削除されるためで、正典は 5.1（呼び出しの形）にある。

## 5. dispatch テンプレート

### 5.0 dispatch の前に、契約 73 章 5 節の該当フェーズの行を読む（毎回。省略不可）

契約 73 章 5 節は「フェーズ別の着手前 worklist 索引」である。そのフェーズが着手前に読むべき章が、フェーズごとに 1 行にまとまっている。

```bash
grep -n -A22 '### 73.5' docs/superpowers/plans/2026-08-01-kamux/00-contracts.md
```

`-A` の値は表の末尾まで届いていることを目で確認する。短く切ると M3-3 / M3-4 の行が落ちる。
「末尾が落ちても出力は正常に見える」のがこの種の欠陥の形である（契約 68 章 1 節）。

- 索引の行を読み、そこに挙がった章を読み、必要なものを brief と dispatch プロンプトに反映する
- 索引は所在だけを持つ。指示の中身は各章にある（73 章 5 節の規律）。ここに表を写さない。写した瞬間に二重の正典になり、片方が腐る
- 新しい章が増えるので、記憶で代用しない。訂正は常に契約ファイルの末尾に増える
- 印の有無を問わず、欄に挙がった全章を開き、開いた章を dispatch に列挙する。印が付いた章だけを拾い、印の無い章を素通りした空振りが実在する
- 観測点: dispatch に 73 章 5 節の欄の全章が列挙されていること。`grep -c '§' <dispatch の該当節>` が欄の章数と一致する

「dispatch 時に適用する」worklist は 38 行・7 フェーズあり、読み落としが繰り返された。どの回も形は「契約に書いてあったが読まれなかった」である。
索引は手数を「7 章を探す」から「1 行を見る」に減らすだけで、読む人がいなければ落ちる。

### 5.1 呼び出しの形

`Agent` ツールを次の形で呼ぶ。`model` は必ず明示する（省略すると親を継承する）。

```
subagent_type: "lane-controller"
name:          "lane-<フェーズ ID 小文字>"     ← SendMessage の宛先になる
               PR 単位で分けるなら末尾に "-pr<n>"、引き継ぎで起こし直すなら
               さらに連番（b, c, …）を足す。例: lane-m2-2-pr17 → lane-m2-2-pr17b
model:         "opus"
description:   "<フェーズ ID> lane"
run_in_background: true
```

`isolation: "worktree"` を使わない。ハーネスの隔離 worktree は「レーンのエージェントが終了し、かつ変更が無い」と自動削除される。
`Agent` は `run_in_background: false` でも非同期で返るため、レーンは implementer を起動した直後に必ず一度終了する。
つまりコミットが 1 つも無い初回タスクの最中は削除条件に必ず当たり、worktree が実際に消えたフェーズが 2 つある。

2（ステージの定義）の表で隔離が必要なステージでは、あなたが手で作ってからパスを渡す（ハーネス管理外なので消えない）。

```bash
git fetch origin
git worktree add .claude/worktrees/<フェーズ ID 小文字> -b <ブランチ> origin/main
(cd .claude/worktrees/<フェーズ ID 小文字> && npm ci)   # node_modules は worktree に無い

# レーンを張り直すときはブランチが既にあるので -b を外す（-b 付きは fatal で落ちる）
git worktree add .claude/worktrees/<フェーズ ID 小文字> <ブランチ>
```

`docs/superpowers/` と `.superpowers/` は `.git/info/exclude` により git 管理外なので、worktree 側に存在しない。
計画・契約・ledger はメイン作業ツリーの絶対パスで渡す（`/Users/ooidetatsuya/repo/kamux/docs/superpowers/...`）。
相対パスで渡すとレーンは「ファイルが無い」と言って止まる。

プロンプトの中身（`<>` を表の値で埋める）:

```
あなたは kamux の <ID> レーンを担当する。

計画: docs/superpowers/plans/2026-08-01-kamux/<計画ファイル>（<タスク数> タスク）
契約: docs/superpowers/plans/2026-08-01-kamux/00-contracts.md
ゴール: <ゴール>
作業ブランチ: <ブランチ>（main から切ること。main で直接作業しない）
作業ディレクトリ: <worktree の絶対パス>（隔離が要るステージのみ。全コマンドを cd <絶対パス> && ... の形にすること）

<このフェーズが全体のどこに位置するか / 後続が何に依存するか を 2〜3 行>

実装は src-tauri/ を rust-implementer、src/ を web-implementer に投げること。
model は sonnet を明示する（設計判断を伴うタスクのみ opus）。

<人間ゲートがあれば: 「<内容> は実機確認が必要なので、着手せず BLOCKED で返すこと」>

マージ許可: あり / なし（契約 §32.3。なしの場合は PR をスタックさせ、マージしない）

契約の不足に気づいたら、自分で 00-contracts.md を編集せず、契約変更要求として上げること。

完了したら完了報告フォーマットで返す。
```

過去タスクの要約や、このセッションの会話履歴を貼らない。
サブエージェントは会話を一切継承しないが、だからといって履歴を貼り付けるのは逆効果である。渡すのは計画ファイルのパスと、上の枠内の情報だけでよい。

並列起動するステージでは、1 回の応答の中に `Agent` 呼び出しを複数書く。1 メッセージ 1 呼び出しは直列になる。

### 5.2 単発の dispatch（レビュー・調査をレーン外で直接依頼するとき）

レーンを経由しない単発の依頼（補償レビュー・棚卸し・検算）には、受け手の定義が要求する入力を必ず渡す。受け手の定義は「渡されなければ聞く／推測しない」を正しく守るので、欠けた欄は毎回同じ往復か推測になる。

1. **ラウンドトークン**（`round: <トークン>`）。無いと `task-reviewer` は完了マーカを書けない
2. **ledger の絶対パス**（参照させる場合。推測で突き合わせさせない）
3. **読み取り / 改変の射程**。「読み取りのみ」と変異検証の許可を同居させない —— 変異を許すなら 4 段手順の明記とセットで書く

観測点: 単発 dispatch の便にこの 3 点が在ること（変異を許さない依頼では 3 は「読み取りのみ。一時改変も不可」の 1 行でよい）。

## 6. 起動後の監督

| 状況 | 対応 |
|---|---|
| 進捗を聞かれた | `TaskList` で一覧、`TaskOutput` で途中経過を覗いて要約する |
| 1 時間以上応答が無い | 停止を疑う。下の「無応答のとき」を見る |
| BLOCKED が返った | 人間ゲートならユーザーに提示し、結果を `SendMessage` でレーンへ返す |
| 契約変更要求が返った | `contract-owner` を起動して裁定させる。同時に走らせるのは 1 体だけ（下記）。裁定結果は並列中の他レーンにも周知する |
| PR が出た | lane-controller がマージまで行う（契約 32 章の 7 条件）。あなたは介入しない |
| `needs-human-verification` の PR で BLOCKED が返った | 検証手順をユーザーに提示 → 結果を受けてラベルを外す → `SendMessage` でレーンへ通知 |
| 引き継ぎ報告が返った | 同じ形で次のレーンを起こす（`name` は 5.1 の規則に従う）。下の「引き継ぎのとき」を見る |
| レーンが完了した | ステージ完了ゲートを実行 → 次のステージへ |
| レビューに修正を返した | 前ラウンドの判定を受け取ってから次の依頼を送る。下の「修正ラウンドのとき」を見る |

無応答のとき。`git -C <worktree> log --oneline -3` と `git status --short` を見る。
動いていなければ `SendMessage` ではなく `Agent` の再起動で再開させる。
`SendMessage` はつねにバックグラウンド実行になり、完了イベントが 1〜2 時間遅れる事象があるためで、再起動せず待って半日の大半を失った日がある。
この 1 時間は「実測ができないまま無証拠で待ってよい上限」であって、待つ間の観測を免除しない。
この行だけを読んで通知待ちで構えてはならず、10 分ごとに見に行く機構を同じ便で張ること（次節）。

引き継ぎのとき。レーンは 2 タスク進むと引き継いで終了する（`lane-controller.md`「2 タスク進んだら引き継いで終了する」）。
報告に書かれた「マージ許可」を次の dispatch にそのまま載せる。フェーズが未完了ならゲートは実行しない。

修正ラウンドのとき。便を交差させると、毎回「判定は既に送信済み」の往復が 1 つ増える。
修正をコミット・push したうえで sha を 1 行送り、判定を待つ。
依頼に測定時 HEAD を要求するのは既に効いており、どちらが古いかは毎回切り分けられる。切り分けられることと、往復が増えないことは別である。

### 事象が起きないことを検知する規則は、能動的な起床機構を同時に置く

無応答・停止・不在を検知する規則は、受動的な通知待ちのままでは構造的に発火しない。検出すべき事象が「通知が来なくなること」だからである。
規則を書いただけでは足りず、その規則を発火させる能動的な起床機構（`Monitor` / `Bash` の `run_in_background: true` による待ちループ）を、同じ便で張って初めて規則になる。
通知待ちで構えている限り「通知が来なくなる」は検出できない。時計で起きる必要がある。

- 欠けるのは閾値ではなく観測の頻度である。1 時間の閾値を持ちながら 2 時間超気づかなかった実例があり、閾値をいくら下げても、見に行く契機が無ければ発火しない。手当ての `Monitor` は 10 分無進捗 / 25 分無進捗で鳴らす
- 沈黙を成功と読まない。発火条件には進捗（ブランチ HEAD か ledger の mtime が動いた）だけでなく、終端状態（PR の `MERGED:` / `CLOSED:`）も入れる。失敗の形を拾わないと、失敗による沈黙が成功待ちに見える
- 張ったあと、その待ち条件の判別力を測る（人間ゲートの検査 5 の軸。本節とは別の軸である）。機構を張ったことと、張った機構が 2 状態を区別することは別の合否である
- 判定基準の正典は `lane-controller.md`「対処 1 の続き」(3) の判定基準ブロック（系統数 / 生存の陽性証拠の由来 / 終端状態の 3 条件）。ここへ写さない。写した 2 版が実際に食い違い、同じ入力に別の評決を出した
- 「まだ書き始めていない」と「死んだ」は、報告ファイルだけを見ている限り同じ観測になる。報告ファイルの mtime 1 点を待ち条件にした機構が、書き始め前の沈黙で誤爆した実例がある
- 「起きたら同じ応答の中で次の一手を打つ」規律とは機構が違う。あちらは起床イベントが届くことを前提に、その後の一手を定める。本節の形は起床条件を 1 つも張っていないので、そのイベントが構造的に来ない。あちらの手当てでは閉じない

時間の値は 3 つ（1 時間 / 20 分 / 10 分）並ぶが、競合しない。判定を時間でしていないからである。

🔴 停止したかどうかは時間ではなく実測で判定する。時間の値は「見に行く契機」であり、判定そのものではない。

| 値 | 誰の値か | 何のための値か |
|---|---|---|
| 10 分 / 25 分 | team-lead の `Monitor`（レーンに対して） | 見に行く契機 |
| タスク境界で 20 分（ループ上限 58 分） | lane-controller の待ちループ（implementer / `task-reviewer` に対して）。正典は `lane-controller.md`「対処 1 の続き」末尾 | 見に行く契機（待つ相手が違うので値も違う） |
| 1 時間（上の監督表） | team-lead（レーンに対して） | 実測ができないまま経過したときに「停止した」と断じてよい上限。最後の手段であって、通常の判定経路ではない |

鳴ったら判定するのではなく、鳴ったら実測する。`git -C <worktree> log --oneline -3` / `git status --short` / `gh pr checks` / 報告ファイルの mtime。
実測で確定するなら 1 時間を待たない。1 時間まで待つのは、実測しても 2 状態を区別できなかったときだけである。

観測点: レーン・`Agent` を起動した便、および「待つ」「様子を見る」と判断した便に、その停滞を検出する機構を張った出力が 1 行あること。
`Monitor` が登録に成功したことを示す出力（`Monitor started (task …)` の行）か、`Bash`（`run_in_background: true`）の待ちループの投入がそれである。

- 起動の便だけを見ては足りない。過去の失敗は起動の便ではなく、idle 通知を受けて「介入しません」と書いて終わった便で起きている
- 見るのは語の存在ではなく登録が成立した出力である。「`Monitor` を張る」「あとで監視する」と書いただけの便は不合格で、過去の失敗とまったく同じ形である
- 本節の観測点は「機構が在るか」までしか見ない。張った機構が 2 状態を区別するかは、人間ゲートの検査 5 の側で測る。どちらか片方だけでは両方の失敗形を防げない

経緯（発生当日の事後分析・`Monitor` の 4 条件の設計）は `.claude/AGENT-LESSONS.md` の事象行に在る。恒久的な引用先は常に台帳を使い、`progress.md` は git 管理外のためここでは引かない。

### 言明の一部だけを測って、残りを前提として扱わない

あなたの断定は指示に変換され、レーンの dispatch を経て implementer まで届く。理由は結論より速く、そして遠くまで伝播する。
測り残しやすいものが 6 つある。

- 理由（結論は正しいのに理由が偽である形。誤った理由は再利用される）
- 観測経路（不在を根拠にした形。不在は「対象が失敗した」証拠にも「観測経路が届いていない」証拠にもなる）
- すぐ確かめられる証拠（ファイルを開けば分かることを断定した形）
- 原因 / 分類の根拠（原因を推定して再発防止を書くと、当事者が「守っていた」と言える形になり、穴が開いたまま閉じたように見える）
- 比較の片側（コード側は測ったのに契約側を前提した形）
- 記録した実測の鮮度（申し送りに書いた実測が古くなったまま次の dispatch で渡される形）

【規則】申し送り・裁定・中継に実測を書くときは、`<値>（<コミット sha> で実測、<日付>）` の形で測った時点を併記する。

- 渡す前に取り直す。申し送りは書かれた時点の真を保存するものであって、鮮度を保証しない
- 同じ問いが brief でも出た（`stat` で計画より新しいことを確認する。`lane-controller.md`「brief のコード片は…」の 3 番目）。索引でも握手でもなく、時刻を残す / 比べるだけで答えられる
- 観測点: 申し送りの実測に sha か日付が併記されていること。併記の無い実測は、渡す前に取り直す対象である

【規則】他者の報告を追認するときは、結論と理由を分けて、理由のほうに実測の出所が書かれているかを見る。書かれていなければ「結論を採る。理由は未確認」と明示して返す。

【規則】結論が複数箇所で同じでも、理由は箇所ごとに別々に測る。

- 「N 箇所で同じ誤った理由」と書いて実際は 1 箇所だけだった実例がある。誤った理由は再利用されるので、当たらない箇所まで「偽」と記録すると、次の読み手が正しい理由まで捨てる（contract-owner が明記）
- 観測点: 「N 箇所が同じ誤りを持つ」と書いた便に、N 箇所を 1 つずつ引いた逐語があること。引けない箇所は件数から外す

差分を機械解析するなら `--no-ext-diff` を付ける。このリポジトリは `diff.external=difft` であり、`git diff <range>` は `^diff --git` を 1 行も出さない。
`^diff --git` が 0 行なのは「差分が無い」ではなく「測れていない」である。

【規則】再発防止を書くときは、その原因が実測か推定かを明記する。推定なら「推定である」と書き、確かめる手順を添える。

【規則】規則が守られたのに悪い結果が出たら、疑う先は 2 つある。規則の書き方（入口）と、規則を満たした後の行き先（出口）である。
先に「規則どおりやった結果どこへ行くか」を辿る。

### 中継の言葉は、対象ごとに書き分ける

実装完了はタスク完了ではなく、レビューが別工程として残る。
「実装完了」の中継に「次のタスクへ進んでよい」と書くと、レビューゲートを免除したように読める。

| 中継の対象 | 書く言葉 |
|---|---|
| implementer の完了 | 「レビューへ dispatch すること」 |
| レビューの `APPROVED` / `PASS` | 「次のタスクへ進んでよい」 |
| 修正ラウンドの完了 | 「再レビューへ進むこと」 |

- 「進んでよい」を実装完了の中継に付けない
- あなたの完了通知の中継は、レーンにとって唯一の権威である（マーカは代替でしかない。`lane-controller.md`「対処 1 の続き」(2)）。中継を怠ると、レーンはマーカに頼るしかなくなる
- 時間依存の指示（「◯◯の前に △△ すること」）には、実行してよい条件を必ず添える。条件の無い時間依存の指示は、受け手がいつ実行しても正しいように見え、実際には正しい瞬間が限られている

### 契約の書き手は同時に 1 体だけ

`contract-owner` を並列に起動しない。複数の裁定が同時に走ると、両方がファイル末尾に新章を足して章番号が衝突する。追記では直せない。
先に書いたほうの番号を後から動かすと、12 計画の相互参照が一斉に陳腐化する。

- 契約変更要求が複数同時に返ってきたら、1 体に直列で queue する（1 回の起動で複数の要求を裁定させてよい）
- 裁定が終わるまで、その論点に触れるタスクは止める

### 人間ゲートの手順は、渡す前に実装で検算する

手順が空振りしても、ユーザーには「不合格」と見分けがつかない。5 つの失敗形を実測している。

| 失敗形 | 何が起きるか |
|---|---|
| 自動テストの緑を根拠にする | 上流ライブラリのバグには自動テストは無情報である。緑でも症状は残る |
| 実在しない観測を指している | 手順が出力・ログ・UI 要素を指しているが、実装にその出力経路が無い。`grep` で確かめれば渡す前に分かる |
| 手順の粒度が粗く、症状が素通りする | 1 文字ずつ打てば現れる現象を「文字列を入力する」と書く形。粒度の正典は契約 71 章 4 節 / 71 章 5 節 |
| 期待値が契約と逆を向いている | そのまま実施すれば契約どおりの正しい実装が不合格になる |
| 期待結果が狭く、不合格の形を含まない | 「開く」までしか書かないと、画面の一部しか埋まらない状態でも合格として通る |

「たぶん通る」で ✅ にしないのと同じ理由で、「たぶん信号が出る」で渡さない。
なお「出力経路はあるが前提条件を作れない」形はこの表の 2 行目に寄せない。機構が違い（2 行目は「出力経路が無い」）、下の検査 4 が持つ。
理由を消すと、次に読む者が同じ寄せ方を再生産できる。

渡す前に 5 つの検査を行う。

1. 観測点の実在確認。手順が触れる出力・ログ・UI 要素を実装側で `grep` する
2. 契約との突き合わせ。期待値がその機能を定める契約章と同じ向きか。手順を書いた人と契約を書いた人が違うので、逆を向いていても誰も気づかない
3. 不合格の形を書く。期待結果は「何が見えれば合格か」だけでなく「どう見えたら不合格か」を必ず 1 行持つ。合格の形しか書かないと、実施者は「それらしく動いた」を合格と読む
4. 前提条件の到達可能性。手順が作ろうとしている状態に、実装から見て本当に到達できるかを確かめる
5. 観測の判別力。「測りたい機構が死んでいても、この観測は出るか」を 1 行書く。出るなら、その項目は機構を測っていない

検査 5 の問いは待ち条件・起床条件にも当てる。
かつて宛先を「変異 / 陽性の対照 / スモークの観測欄」と書いていたため、`Monitor` や待ちループの条件が射程外に落ち、報告ファイルの mtime 1 点だけを見る機構が誰の検査にも掛からなかった。
「自分で設計した観測」であれば、それが検証のためか起床のためかは関係ない。

検査 5 は検査 1〜3 と別物である。検査 1 は「観測経路が在るか」、検査 3 は「不合格の読み方」を見る。
検査 5 は「観測経路も在り不合格の形も書いてあるのに、機構が死んでいても合格が出る」形を見る。

観測点: 手動スモークの各項目に「この観測は、測りたい機構が死んでいても出るか」への答えが 1 行あること。`grep -c '機構が死んでいても' <手順>` が項目数と一致する。

検査 1〜3 はすべて「出口」を見ている（信号が出るか / 向きが正しいか / 読み方）。「入口」は検査 4 だけが見る。
3 検査に逐語で通した結果 3 つとも合格するのに、手順が必ず空振りする形が実在した。

- 確かめ方: 手順が変える対象を実装側で `grep` し、実装がその値を読んでいることまで辿る。「その名前の変数がある」で止めない。同名の別経路であることがこの穴の正体である
- 観測点: 手動スモークの項目それぞれについて「どの変数／状態を、どの経路で変えるか」が 1 行書かれていること。書けない項目は、前提条件を作れていない疑いがある

管轄の分界。二重の正典にしないため必ず読むこと。

| 誰の義務か | 正典 |
|---|---|
| 人間ゲート項目を書く者（契約自身 / 計画 / レーン）。項目に現れる名詞 / 操作 / 観測のそれぞれにリポジトリ内の一次証拠を 1 つ挙げる | 契約 105 章 5 節（+ 107 章 4 節が「観測」欄に問いを 1 つ足した） |
| 項目を実施者へ渡す前に team-lead が走らせる検算 = 上の 5 検査 | 本節。契約 105 章 5 節 2 が「契約の管轄外。転写するかどうかは team-lead が決める」と明記している |

本節は 105 章 5 節を写していない。写すと二重の正典になる。3 欄は「項目に現れる具体物を数える」、5 検査は「その項目が信号を生むか」を見る。軸が違う。

107 章 4 節の問いを、検査 1 に必ず併せて当てること。
「その値の読み手は人間の目だけか。機械が読める出力が別に在るなら、そちらを正典にする。探した結果『無かった』なら、探したことと探し方を項目に書く」。
人間の目だけを読み手にした項目は「見えなかった」と「出ていなかった」が同じ報告になる。

### 規則を書いた便には、その規則をその便自身へ当てる

「規則を当てる工程を、渡す前に 1 回入れる」と射程が違う。あちらは「他者へ渡す項目」に当てる話、本節は「自分が今書いた文章」に当てる話である。

【規則】規則・裁定・申し送りを書いた便を送る前に、その規則をその便自身へ 1 回当てる。「書いた」ではなく「当てた」である。

節の見出しを改名・新設したら、他の定義ファイルからのその見出しの引用を `grep` で当てる。引く向きは 2 つあり、片方だけでは落ちる。

```bash
# 向き 1: 見出しの語 → 誰が引いているか（引用の不在を見る）
grep -n '<見出しの語>' .claude/agents/*.md .claude/skills/kamux-lane/SKILL.md
# 向き 2: 引用の文字列 → 実体が在るか（引用の切れを見る）。こちらを落とすと装飾で切れた引用が残る
grep -n '「[^」]*」' .claude/AGENT-LESSONS.md   # 棚卸し表の所在列から引用を拾い、1 つずつ実体を探す
```

- 比較は記号と空白を正規化してから行う。見出しに装飾が入り引用が省略形だと、素の `grep` は 0 を返す
- ヒットした行を 1 つずつ開き、指している節が実在することまで確かめる。`grep` の非空は「その語がある」しか言わない
- 向き 3: **編集したファイル自身の中**。挿入・書き直しは、同一ファイル内の既存ブロック（引用・表・所在列）を割りうるが、割れたかは旧版との対照でしか決まらず、直前行だけを見る検査には出ない。編集後に `git diff --no-ext-diff`（追跡外ファイルは編集前コピーとの `diff`）で、**自分が触るつもりの無かった行が変わっていないこと**を見る。観測点: 挿入・書き直しの便に、対照 diff で「意図した編集行以外 0 行」を確かめた出力があること
- markdown を機械検査するときは code span を先に落とす。code span 内の記号を数えると偽陽性が出る。「2 者が独立に測って一致した」は、2 者が同じ道具を使っていれば独立ではない
- 観測点: 規則を書いた便に「その規則を自分の出力へ当てた結果」が 1 行あること。昇格 PR では、新設した必須項目をその PR 自身の全群へ当てた表があること

【規則】手当ては「気をつける」ではなく、打つコマンドの形にする。警告文だけで閉じた項目は、次の便で同じ形を打たれる。

観測点: 罠を記録した報告に、その罠を回避する具体コマンドが 1 行あること。「注意する」「気をつける」で終わっている手当てが 0 件であること。

### 証拠に借りたコマンドの出力が、2 状態を区別するか

観測の判別力（人間ゲートの検査 5）と機構が違う。こちらは既存のコマンド・既存の指標を借りてきて証拠に使い、その出力が「成立」と「不成立」で同じになる形である。
手当ても違う。設計時ではなく使用時に「不合格のとき何が見えるか」を書く。

【規則】既存コマンドの出力・既存の指標を証拠として使う前に、「不合格のとき何が見えるか」を 1 行書く。書けないコマンドは証拠にしない。
「終了ステータス 0」「出力が空」「件数が同じ」は、それ自体では成立の証拠にならない。

| 借りた出力 | 2 状態を区別しない形 |
|---|---|
| パイプの終了ステータス | `cargo test --workspace 2>&1 \| tail -20` の終了コードは `tail` のものである。手前が落ちていても緑と報告する形になる |
| `git push -q origin main` | HEAD 違いでローカル `main` を push すると無変化で成功し、`-q` と相まって成功と区別が付かない |
| `rm -rf` に glob | zsh の no-match でコマンド全体が中断し、先行パターンの削除が 1 つも実行されない。終了ステータスからは「消した」と「1 つも消さずに中断した」を区別できない |
| `gh pr merge --delete-branch` | worktree から打つと失敗に見えるが、実際はマージ済みでありうる（`state=MERGED` / `mergedAt` あり / `git ls-remote --heads origin <br>` = 0 件） |
| `git ls-files -s` / `git status --porcelain` | 前者はインデックスのモードを返すので worktree の実行ビット喪失を見ない。後者は `.gitignore` 配下の成果物を見ない |
| `cargo test --workspace`（`--no-fail-fast` 無し） | 先頭 target が赤になると残り target が黙って飛ぶ |
| CI / ローカルの緑 | ローカルと CI が構造的に別物になる形がある（gitignore 配下のビルド成果物など）。片方の緑はもう片方の緑を意味しない |
| テスト本数 | アサーション反転は本数が変わらないので「本数が減っている差分で判定する」規則の網に掛からない |

観測点:

- 証拠に使った各コマンドについて「不合格ならこう見える」の 1 行が報告・手順に在ること
- `gh pr merge` がエラーを返した記録には、必ず `gh pr view <n> --json state,mergeCommit` の出力が続いていること
- 後片付けの glob に `(N)` か `2>/dev/null` が付いていること。`cargo test --workspace` に `--no-fail-fast` が付いていること
- 検証コマンドを `| tail -n` にパイプしないこと。各コマンドを単独で走らせ `$?` を読む。ゲート記録の各行に `exit <n>` が書かれていること。書かれていない行はパイプで測った疑いがある

### 検査と是正の順序

検査は、その結果を反映できる状態が残っている時点に置く。検査の時点で是正経路が既に閉じていると、指摘は「記録」にしかならない。

【規則 0】判定（レビュー・承認・裁定）を依頼したら、判定が返るまで**その対象を凍結する**。対象はコミット済みブランチに限らず、未コミットの成果物・検算スクリプト・手順書・器も含む。判定区間に対象を動かす必要が生じたら、動かす前に依頼を取り下げる便を出す。

- 依頼の便に対象の同定（sha / ファイルと mtime）を書き、判定を受領した便で同じ値を再掲して一致を確かめる。一致しないなら判定は動いた対象を見ていない
- この規則は依頼を出す側（team-lead / lane-controller）に掛かる。implementer は dispatch されない限り書かない。**task-reviewer は変異検証で production を一時改変する**（`task-reviewer.md` の 4 段手順）—— 判定区間の凍結は依頼側の義務だが、**同じ作業ツリーで測る第三者（ゲートのビルド等）が居るときは、依頼側が隔離 worktree を切ってから依頼を出す**（変異込みのバイナリを掴んだ実測がある）
- 観測点: 判定受領の便に、依頼時と同じ sha / mtime の再掲があること

【規則 1】マージ許可を出す前に `git diff --no-ext-diff --stat <承認 sha>..HEAD` を測り、非空ならレビューへ戻す。
PR 本文に「承認後にコミットを積んだ」と明記するのは口頭補填であって、定義側の手当てではない。

観測点: マージ許可の記録に `git diff --no-ext-diff --stat <承認 sha>..HEAD` の出力が引かれており、空でないなら再レビューの記録が続いていること。

フェーズ完了時は必ず非空になる。例外にしない。
規則 2 が全ブランチレビューをマージ前へ移した結果、その指摘への修正が最後の PR のブランチへ積まれ、`<承認 sha>..HEAD` は構造的に非空になる。
正しい閉じ方は「例外を作る」ではなく「再レビューを 1 回通し、その `APPROVED` の sha を次の測定の起点にする」である。

- 根拠は契約 101 章 4 節。「条件 3 の取り直しが要るのはコンフリクト解決が発生したときだけ」と定め、その理由を「解決結果は誰もレビューしていない著作物であり、条件 3 の射程そのものである」と書いている。全ブランチレビューの指摘を直した差分は、まさに「誰もレビューしていない著作物」である
- ただし 101 章 4 節は本件を逐語では governs しない。原理が転移するだけである。101 章 4 節の見出しと正典ブロックの前置きは、自分の射程をコンフリクト解決に明示的に限定している。「承認後にコミットを積んだ」を直接 governs する章は契約に 1 つも無い（`grep -cE '承認後|承認の後|APPROVED の後'` = 0）
- 転移するのは理由列が事象ではなく性質で書かれているからである。「コンフリクト解決」ではなく「誰もレビューしていない著作物」。修正コミットはその性質を満たす
- この但し書きを落とすと壊れる形が実在する。101 章 4 節を開いた読み手が「だけ」と前置きに行き当たり、「修正コミットにコンフリクト解決は発生していない → 条件 3 の取り直しは不要」に到達できる。本節が防ごうとしている「再レビューを飛ばす」が、本節の引用文そのものから出る
- 32 章の条件 3 の逐語は「PR の差分全体に対して 1 回」であり、承認対象の sha を名指ししていない。手順は `.claude/references/lane-controller-completion.md`「フェーズ完了時の手順」の手順 3 が持つ（順序規則の正典は `lane-controller.md`「フェーズ完了時」）

【規則 2】全ブランチレビューは、ブランチが存在する間に実施する。
「最後の PR をマージ → 全ブランチレビュー → 修正」の順だと、レビュー時点でブランチは `--delete-branch` で消えており、修正が構造的に実行できない。毎フェーズの最後で必ず起きる形である。

観測点: `.claude/references/lane-controller-completion.md`「フェーズ完了時の手順」の節の中で、番号付き手順の「全ブランチレビュー」が「最後の PR をマージする」より小さい番号を持つこと。

```bash
awk '/^## フェーズ完了時の手順/,/^## E2E とスモークの仕分け/' .claude/references/lane-controller-completion.md | grep -nE '^[0-9]+\. '
```

ファイル全体に `grep` を当ててはならない。どちらの語も別の節や引用の中に先に現れるので、初出の行番号を比べると節の順序と無関係な答えが出る。
合格と不合格を区別しない観測点は、上の節（証拠に借りたコマンドの出力）の形そのものである。

なお「台帳への転記路がマージと同時に閉じる」形は本節では閉じない。中継・転記の規律の側が持つ。

### 同じ作業に実体は 1 体だけ

「契約の書き手は同時に 1 体だけ」を一般化する。
契約に限らず、作業を割り当てる側が「その作業に既に就いている実体」を測らずに新しい実体を立てると、二重に走る。

【規則】実体を起動する前・降りた相手へ便を送る前に、「この作業に既に就いている実体は何体か」を 1 コマンドで数える。
引き継ぎ報告を返して終了したレーンへ `SendMessage` を送ると再稼働する。追加の指示は必ず後継へ送る。

観測点:

- 起動指示に `ListAgents` の出力か「先行レーンは停止済み（最終応答 <時刻>）」の 1 行があること
- 引き継ぎ後に前任へ送った `SendMessage` が 0 件であること（送った記録が在るなら、後継を立てていないことが同じ便に書かれていること）
- 「未適用」として渡した箇所は、渡す直前に測った `grep` / `git diff --no-ext-diff` の出力が併記されていること

### 稼働中の他者が使っている状態へ書かない

【規則】`git commit` / `git push` / 成果物の上書きを打つ前に、その作業ツリー・ブランチ・成果物を参照している他の実体を測る。
`git status --porcelain` はこれを構造的に見ない。

隔離不要のステージでは team-lead とレーンが同じチェックアウトを共有しており、`git commit` はそのとき出ている HEAD に落ちる。
また、手当てとして常設 worktree（main を占有）を作ると、今度はレーンの `gh pr merge --delete-branch` を失敗させる。常設にせず、必要なときに作って消す。

観測点: team-lead が `git commit` を打つ記録に、直前の `git -C <絶対パス> rev-parse --abbrev-ref HEAD` の出力が併記されていること（レーンのブランチ名なら不合格）。
`git worktree list` で稼働中レーンのチェックアウトを確かめた出力が在ること。

### 裁定は `SendMessage` を待たず、契約ファイルの末尾を読む

中継する側（team-lead）の義務である。適用者側の義務は `lane-controller.md` / `contract-owner.md` が持つ。

【規則】裁定を中継したら、その便に「契約のどの章に着地したか」を章番号で書く。中継が届かなくてもレーンが自力で到達できるよう、章番号を渡す。
中継と引き継ぎが行き違うと、その間 ledger には裁定済みの件が未処理として書かれ、次の読み手が二重に上げうる状態が残る。

観測点: 裁定を中継した便に契約の章番号が書かれていること。`progress.md`「## 裁定」に同じ内容が書かれていること（`SendMessage` はリポジトリに何も残さない）。

### 工程を定義したら、産物の書き先・書き手・時点を同じ場所に書く

「裁定と実施記録は、リポジトリに残る形で渡す」の一段手前である。あちらは「書いた物が残るか」、本節は「そもそも誰がいつどこへ書くかが決まっているか」を見る。

【規則】工程を定義したら、その産物を「誰が・いつ・どこへ」書くかを同じ場所に書く。

観測点 1: `grep -c '後で実施\|次の PR で\|別作業' <ledger>` が返した各行に、同じファイル内に結果の行が対で存在すること。
観測点 2: ゲートの実施記録を持つ `progress.md`「## 裁定」の本数が、実施済みのステージ数以上であること。

```bash
# glob を使わない。zsh の no-match はリダイレクトより前にコマンド全体を中断するので、
#    `2>/dev/null` を付けても「0 件」と「1 つも走らなかった」が同じ出力になる
# -c ではなく -l で数える。-c はファイルごとの件数を並べるので合計と比較できない
# メインの作業ツリーで打つこと。.superpowers/ は worktree には存在しない
R=<リポジトリの絶対パス>
find $R/.superpowers/sdd -name progress.md 2>/dev/null | wc -l                                        # ① 母数
find $R/.superpowers/sdd -name progress.md 2>/dev/null \
  | xargs grep -l '^## 裁定' 2>/dev/null | xargs grep -l 'ステージ完了ゲート' 2>/dev/null | wc -l        # ② 実施記録を持つ本数
find $R/.superpowers/sdd -name TEAM-LEAD-RULINGS.md 2>/dev/null \
  | xargs grep -l 'ステージ完了ゲート' 2>/dev/null | wc -l                                             # ②' 統合前フェーズの実施記録本数
```

- ① を必ず先に出す。① が 0 なら「実施記録が無い」ではなく「そもそも測れていない」である（ディレクトリが無い / 打った場所が違う）。判定は ②+②' が実施済みステージ数以上であること
- `TEAM-LEAD-RULINGS.md` から `progress.md`「## 裁定」への統合（issue #90）より前に完了したフェーズの実施記録は移行しない。②' 側に残ったまま数える。移行すると過去のフェーズ側で二重カウントか消失が起きる

### 原本が在る値を手で写さない

「二重の正典にしない」を、規則ではなく値へ広げる。

【規則】原本が実在する値・規則を、別の場所へ手で写さない。写す必要があるなら、写した先に原本の所在（`<ファイル>:<行>`）を併記する。
規則を 1 ファイルから削るなら、同じコミットで他ファイルへ新設していないことを `grep` で測る。

観測点: 人間ゲートの手順に、値を手で書いた行が 0 行であること（実コードを実行して出力させる形になっていること）。
規則を削ったコミットで `git diff --no-ext-diff -U0 | grep '^+' | grep -c '<削った閾値>'` = 0 であること。

### 列挙・件数は機械で導出して突き合わせる

【規則】列挙・件数が機械で導出できるなら、導出して突き合わせる。目視で数えた列挙は差集合（`comm -23`）で取り直す。
「N 件」と宣言した見出し・表・行は、実体の件数と突き合わせる。台帳へ行を足すときは列数を数える。
行数検算は表が割れていても合格を返す（総行数は増えているため）。捕まえるのは列数検算だけである。

観測点: 列挙を含む節に、それを導出したコマンドの出力が併記されていること。
「N 行」「N 件」と書いた見出しの直後の表について `grep -cE '^\| '` が N と一致すること。
台帳へ行を足した便に `awk '{print split($0,a,"\|")}' | sort | uniq -c` の出力があること（新規行が n=9 になっていること）。

### 「この規則は本件には当たらない」と書くとき

規則が無いのではなく、規則の適用外だと論証してしまう形である。規則を知らずに破るより見つけにくい。

【規則】「転移しない」「本件には当たらない」「射程外」と書くときは、その規則が生まれた事象を名指しし、そこでの理由が本件で偽になることを 1 行で示す。

観測点: `grep -n '転移しない\|適用外\|本件には当たらない' <契約 / RULINGS>` の各行の直後 3 行以内に、台帳行番号か契約章番号の引用があること。

### 数値には単位・時点・母数の定義を添える

【規則】他者が読む恒久記録すべて（PR 本文・production の doc・起動指示・引き継ぎ）に書く数値には、単位・時点（sha または日付）・母数の定義を添える。
sha を引くときは `git merge-base --is-ancestor <sha> origin/main` が真になるものだけを引く。squash で到達不能になった sha を引いた実例がある。

観測点: `grep -n '[0-9]\+ passed\|+[0-9]\+ / -[0-9]\+' <PR 本文 / doc>` の各行に sha か日付が併記されていること。
引用した sha に `git merge-base --is-ancestor <sha> origin/main` が 0 を返すこと。起動指示の数値に単位が書かれていること。

### 本ファイル内の 2 箇所が食い違ったら、それは定義の穴である

【規則 a】本ファイル内の 2 箇所が食い違ったら、どちらに従っても他方に違反するので自力で選ばない。BLOCKED として上げる。

【規則 b】計画と契約が食い違ったら、「該当 0 件」の `grep` を証拠として添えて裁定要求を上げる。

観測点: 食い違いが BLOCKED として上がった記録が在ること。裁定要求に `grep -c` の出力が添えられていること。

### 規則を当てる工程を、渡す前に 1 回入れる

【規則】人間ゲートの項目を渡す前に、その項目に規則を逐語で当てた結果を 1 行書く。「規則を読んだ」ではなく「当てた」である。規則が在ることは、当てたことを意味しない。

team-lead の検査は項目の「主張」を見ており、実施者が触る「具体物」を見ていない。
一次証拠の 3 欄（名詞 / 操作 / 観測）の規律が成立した当日に、それが捕まえるはずの穴を素通りさせた実例が退避先にある。

### 測定を指示するときは、測る対象を名指しする

「◯◯を測れ」ではなく「◯◯を、△△から、□□に対して測れ」と書く。落ちるのはいつも修飾語のほうである。

平均値を根拠に設計判断をしない。効くのは着地した瞬間の値だけで、平均はそれを平滑化して隠す。

### 裁定と実施記録は、リポジトリに残る形で渡す

`SendMessage` で渡した内容はリポジトリのどこにも残らない。
同じ形で、やると宣言した工程の実施記録が残らない事故も起きている。予告だけが書かれた工程は、実施済みか未実施かを後から判別する手段が無い。

- 裁定は `SendMessage` と同時に `progress.md`「## 裁定」へ書く
- 「後で実施する」と書いたら、実施したときに同じ場所へ結果を書く。予告だけが残っている工程は、未実施として扱う

【規則】恒久的な引用先は、常に `.claude/AGENT-LESSONS.md` の事象行を使う。`progress.md`（本節の「## 裁定」を含む）を恒久的な引用先にしない。

`progress.md` は `.superpowers/sdd/<phase>/` 配下にあり git 管理外なので、定義ファイルから「経緯は `progress.md` の◯◯にある」と書いても、他の worktree や clone からは実体が無い。
本節が `progress.md` を書き先に定めているのは「今動いているフェーズの中で稼働中のレーンが読む」ためであり、恒久的な参照先としての性質を持たせるためではない。

観測点: `.claude/agents/*.md` / `SKILL.md` 内で「経緯」と `progress.md` を同じ行に含む箇所を列挙し、既知の 4 件を超える増分が 0 件であること。

```bash
grep -rn '経緯' .claude/agents/*.md .claude/skills/kamux-lane/SKILL.md | grep 'progress\.md' | wc -l
```

既知の 4 件の内訳（この規律を新設した時点の実測）:

- 1 件は正当な例外（起床機構の節の末尾。台帳を正しく引いた上で、否定文脈で触れているだけの行）
- 3 件は本節（この規律自体を説明する段落）

この `grep` は機械的に 0 件へは収束しない。本節自身が「経緯」と `progress.md` を両方含む自己言及のためである。
正規表現で自己言及分だけを除外しようとすると、表記揺れのたびに壊れる。既知件数との数値比較にとどめ、内訳の是非は増えたときだけ目視するほうが頑健である。
件数が 4 を超えたら、増えた行が「新しい正当な例外」か「規律に違反する誤引用」かを判定する。

### マージ許可（契約 32 章 3 節）—— あなたが出す

| ステージ | 出し方 |
|---|---|
| 単独レーン（stage0 / 2 / 5 / 6） | 起動時のプロンプトに「マージ許可あり」と書く。PR は毎回 `main` から切られ、緑になり次第マージされる |
| 並列レーン（stage1 / 3 / 4） | マージ順で先頭のレーンにだけ「マージ許可あり」と書く。後発レーンには「マージ許可なし」と書き、PR をスタックさせる。先頭レーンが全 PR をマージし終えたら、`SendMessage` で次のレーンに許可を出す |

マージ許可を出す便には、その時点で条件が閉じているかを明記する。

- 「マージ許可: あり。追加条件なし」または「マージ許可: あり。残る条件は N 件（列挙）。それ以外は足さない」
- 許可を出した後に条件を足す必要が生じたら、条件を送るのではなく許可を一旦取り下げる便を先に出す。取り下げが届かないうちに進んでも、レーンに責任は無い
- 許可が下りている状態で、後から来るかもしれない条件を待つ理由はレーン側に無い。逆順（条件を待って止まる）だと 1 時間単位で止まる
- 観測点: マージ許可の便に「追加条件なし」または条件の件数が書かれていること

番号外の PR（どのタスクにも属さない変更）は、PR 単位レビューが唯一の網になる。
通常の PR はタスク単位レビューも通っているので二重の網があるが、番号外の PR はタスク単位レビューに一度も掛からない。

観測点: 番号外 PR のマージ許可に、PR 単位レビューの承認が明示的に引用されていること。

プロンプトに許可の有無を書き忘れると、lane-controller は「許可なし」として扱い確認を求めてくる。
並列ステージで両方に許可を出してはならない。stage1（M1-2 ∥ M1-3）は `App.tsx` / `store/index.ts` / `useKeymap.ts` が重衝突するため、交互にマージすると後発レーンが毎回コンフリクトする。

- 報告に「空」とあるとき、対象が行に割れうる形を 1 つ挙げて確かめた記録が添えられているかを見る（義務の正典は `contract-owner.md` のドリフト検査ブロック。ここへ手順を写さない）
- 併せて「検査の向き」を見る。A→B を測る検査は B→A を測らない。両方向が要るなら 2 本書く
- パターン検査は、対象が別の形（別 API・行に割れる・別の綴り）を取りうるかを 1 つ挙げて確かめる

確認 3 について。閾値・昇格 PR の要件・人間承認ゲートの唯一の正典は `kamux-promotion` であり、本ファイルには書き写さない（写した瞬間に二重の正典になり、片方だけ直せば静かに乖離する）。
起動したこと自体の実施記録を 1 行残す（書き先は「裁定と実施記録は、リポジトリに残る形で渡す」の節）。
ポインタは、踏まれたかを確認する手段が無ければ空振りする。「`kamux-promotion` を起動した」と書かれた行が無い回は、未実施として扱う。

## 7. やってはいけないこと

- 実装 implementer を並列に起動する（レーン内は必ず直列。1 レーン = 1 worktree であって「分ければ並列にできる」ではない）。並行編集で作業が実際に消失したことがあり、消失しなくてもレビュー範囲が汚染される
- `contract-owner` を並列に起動する（章番号が衝突し、追記では直せない）
- team-lead 自身がコードを直す（レビューを迂回し、あなたのコンテキストが汚れる）
- `.claude/agents/*.md` と本 `SKILL.md` の変更を、レビューを通さずに入れる。定義ファイルはすべてのレーンの振る舞いを決めるので、実装コードより差分レビューが要る。
  team-lead が書いてよいが、`task-reviewer` を PR の差分に 1 回かけてからマージする（昇格 PR も同じ。正典は `kamux-promotion`「昇格 PR の進め方」）
- 🔴 昇格 PR をレビュー承認と CI 緑だけでマージする。昇格 PR はユーザー本人の承認が要る（`kamux-promotion`「ユーザーの承認」）
- `00-contracts.md` を lane-controller や implementer に編集させる（章番号がずれると 12 計画の参照が一斉に陳腐化する）
- 🔴 人間ゲートを「たぶん通る」で ✅ にする（headless で再現しない項目を通ったことにするのが、この計画で最も危険な失敗）
- stage5 を並列にする（10 ファイル衝突。得られる時間より統合コストが上回る）
