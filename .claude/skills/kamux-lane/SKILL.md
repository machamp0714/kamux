# kamux レーン起動

`docs/superpowers/plans/2026-08-01-kamux/` の実装フェーズを `lane-controller` エージェントとして起動する。**あなた（team-lead）はレーンを起動して監督するだけで、コードは書かない。**

引数の形は 2 つ。

| 引数 | 動作 |
|---|---|
| `M1-1` 〜 `M3-4` | そのフェーズを 1 本だけ起動する |
| `stage0` 〜 `stage6` | そのステージのレーンを**1 メッセージ内でまとめて**起動する（= 並列実行） |

引数が無い場合は、ledger（`.superpowers/sdd/*/progress.md`）と `git log` から現在地を推定し、次に来るステージを提案してから確認を取る。

# 2. 作業ツリーが汚れていないか

# 3. 直前のステージの成果がマージ済みか
git log --oneline -5

`lane-controller` が利用可能エージェント一覧に出ていない場合は**セッション再起動が必要**。フォールバックとして `subagent_type: "claude"` で起動し、`.claude/agents/lane-controller.md` の本文をプロンプト冒頭に貼る。

## 2. ステージの定義

依存グラフから導出済み（`TEAM.md` §1）。**並列度は最大 3。** クリティカルパスは 7 フェーズ直列なので、レーンを増やしても縮まない。

| ステージ | レーン | isolation | マージ順 | 備考 |
|---|---|---|---|---|
| stage0 | M1-1 | 不要 | — | 全フェーズをブロックする土台 |
| stage1 | M1-2 ∥ M1-3 | **両方 worktree** | **M1-2 → M1-3** | `App.tsx` / `store/index.ts` / `useKeymap.ts` / `package.json` が重衝突 |
| stage2 | M1-4 | 不要 | — | M1-1〜M1-3 すべてが前提 |
| stage3 | M2-1 ∥ M3-1 | 両方 worktree | **M2-1 → M3-1** | 衝突は `main.rs` / `App.tsx` の追記のみ。M3-1 の前提は M1-3 だけなのでここに前倒し |
| stage4 | M2-2 ∥ M2-3 ∥ M3-2 | **M2-2 / M2-3 のみ** | **M2-2 → M2-3 → M3-2** | M3-2 は純フロントで衝突ゼロ（隔離不要） |
| stage5 | M3-3 → M2-4 | 不要 | 直列 | **並列にしない。** Rust/フロント両側で 10 ファイル衝突する |
| stage6 | M3-4 | 不要 | — | M1-1〜M3-3 すべてが前提 |

**stage5 は 1 メッセージ 1 起動（直列）。** M3-3 の完了を待ってから M2-4 を起動する。

**isolation 列が「worktree」の行は、`isolation: "worktree"` ではなく `git worktree add` で手動作成する**（§5.1。ハーネスの隔離 worktree は自動削除される）。

## 5. dispatch テンプレート

### 5.0 dispatch の前に、契約 §73.5 の該当フェーズの行を読む（**毎回。省略不可**）

**契約 §73.5 は「フェーズ別の着手前 worklist 索引」である。** そのフェーズが着手前に読むべき章がフェーズごとに 1 行にまとまっている。

```bash
grep -n -A22 '### 73.5' docs/superpowers/plans/2026-08-01-kamux/00-contracts.md
```

**`-A` の値は表の末尾まで届いていることを目で確認する。** 短く切ると **M3-3 / M3-4 の行が落ちる** —— 「末尾が落ちても出力は正常に見える」のがこの種の欠陥の形である（契約 §68.1）。

- **索引の行を読み、そこに挙がった章を読み、必要なものを brief と dispatch プロンプトに反映する**
- **索引は所在だけを持つ。指示の中身は各章にある**（§73.5 の規律）。**ここに表を写さない** —— 写した瞬間に二重の正典になり、片方が腐る
- **新しい章が増えるので、記憶で代用しない。** 訂正は常に契約ファイルの末尾に増える
- **🔴 印の有無を問わず、欄に挙がった全章を開く。開いた章を dispatch に列挙する**（群 G。2026-08-15 に追加）<br>**なぜ: 2026-08-14、§73.5 の M2-4 欄を読みながら 🔴 が付いた 2 章（§119 / §122）だけを拾い、印の無い `§63` を素通りした**（台帳 #177。**索引の空振り 4 回目**）。**§63.7 は逐語で「`resume_session` が既存の起動経路を通る」を M2-4 の dispatch 時 worklist として持ち、契約 §123 の最強の根拠だった。**<br>**観測点: dispatch に §73.5 の欄の全章が列挙されていること**（`grep -c '§' <dispatch の該当節>` が欄の章数と一致する）

> **なぜ手順に組み込むか: 「dispatch 時に適用する」worklist は 38 行・7 フェーズあり、2026-08-05 に 3 回連続で落とした。** 3 回とも形は「契約に書いてあったが読まれなかった」である。**索引は手数を「7 章を探す」から「1 行を見る」に減らすだけで、読む人がいなければ落ちる。**

### 5.1 呼び出しの形

`Agent` ツールを次の形で呼ぶ。**`model` は必ず明示する**（省略すると親を継承する）。

```
subagent_type: "lane-controller"
name:          "lane-<フェーズ ID 小文字>"     ← SendMessage の宛先になる
               PR 単位で分けるなら末尾に "-pr<n>"、引き継ぎで起こし直すなら
               さらに連番（b, c, …）を足す。例: lane-m2-2-pr17 → lane-m2-2-pr17b
model:         "opus"
description:   "<フェーズ ID> lane"
run_in_background: true
```

**`isolation: "worktree"` を使わない。** ハーネスの隔離 worktree は「レーンのエージェントが終了し、かつ変更が無い」と自動削除される。**`Agent` は `run_in_background: false` でも非同期で返るため、レーンは implementer を起動した直後に必ず一度終了する** —— コミットが 1 つも無い初回タスクの最中は削除条件に必ず当たり、**M1-2 と M2-1 で実際に worktree が消えた。**

§2 の表で隔離が必要なステージでは、**あなたが手で作ってからパスを渡す**（ハーネス管理外なので消えない）。

```bash
git fetch origin
git worktree add .claude/worktrees/<フェーズ ID 小文字> -b <ブランチ> origin/main
(cd .claude/worktrees/<フェーズ ID 小文字> && npm ci)   # node_modules は worktree に無い

# レーンを張り直すときはブランチが既にあるので -b を外す（-b 付きは fatal で落ちる）
git worktree add .claude/worktrees/<フェーズ ID 小文字> <ブランチ>
```

**`docs/superpowers/` と `.superpowers/` は `.git/info/exclude` により git 管理外なので、worktree 側に存在しない。** 計画・契約・ledger は**メイン作業ツリーの絶対パス**で渡す（`/Users/ooidetatsuya/repo/kamux/docs/superpowers/...`）。相対パスで渡すとレーンは「ファイルが無い」と言って止まる。

プロンプトの中身（`<>` を表の値で埋める）:

```
あなたは kamux の <ID> レーンを担当する。

計画: docs/superpowers/plans/2026-08-01-kamux/<計画ファイル>（<タスク数> タスク）
契約: docs/superpowers/plans/2026-08-01-kamux/00-contracts.md
ゴール: <ゴール>
作業ブランチ: <ブランチ>（main から切ること。main で直接作業しない）
作業ディレクトリ: <worktree の絶対パス>（隔離が要るステージのみ。全コマンドを cd <絶対パス> && ... の形にすること）

<このフェーズが全体のどこに位置するか / 後続が何に依存するか を 2〜3 行>

実装は src-tauri/ を rust-implementer、src/ を web-implementer に投げること。
model は sonnet を明示する（設計判断を伴うタスクのみ opus）。

<人間ゲートがあれば: 「<内容> は実機確認が必要なので、着手せず BLOCKED で返すこと」>

マージ許可: あり / なし（契約 §32.3。なしの場合は PR をスタックさせ、マージしない）

契約の不足に気づいたら、自分で 00-contracts.md を編集せず、契約変更要求として上げること。

完了したら完了報告フォーマットで返す。
```

**過去タスクの要約や、このセッションの会話履歴を貼らない。** サブエージェントは会話を一切継承しないが、だからといって履歴を貼り付けるのは逆効果（実セッションで dispatch が 42k 文字に膨れ、99% が貼り付けた履歴だった事例がある）。渡すのは計画ファイルのパスと、上の枠内の情報だけでよい。

並列起動するステージでは、**1 回の応答の中に `Agent` 呼び出しを複数書く**。1 メッセージ 1 呼び出しは直列になる。

## 6. 起動後の監督

| 状況 | 対応 |
|---|---|
| 進捗を聞かれた | `TaskList` で一覧、`TaskOutput` で途中経過を覗いて要約する |
| **1 時間以上応答が無い** | **停止を疑う。** `git -C <worktree> log --oneline -3` と `git status --short` を見る。動いていなければ `SendMessage` ではなく **`Agent` の再起動**で再開させる（`SendMessage` はつねにバックグラウンド実行になり、完了イベントが 1〜2 時間遅れる事象がある）。2026-08-05 はこれで 4 回・計 3 時間半以上を失った<br>**🔴 この 1 時間は「実測ができないまま無証拠で待ってよい上限」であって、待つ間の観測を免除しない**（群 ξ。下の「事象が起きないことを検知する規則は…」）。**この行だけを読んで通知待ちで構えると 2 時間 14 分になる。10 分ごとに見に行く機構を同じ便で張ること** |
| BLOCKED が返った | 人間ゲートならユーザーに提示し、結果を `SendMessage` でレーンへ返す |
| 契約変更要求が返った | `contract-owner` を起動して裁定させる。**同時に走らせるのは 1 体だけ**（下記）。裁定結果は**並列中の他レーンにも周知する** |
| PR が出た | **lane-controller がマージまで行う**（契約 §32 の 7 条件）。あなたは介入しない |
| `needs-human-verification` の PR で BLOCKED が返った | 検証手順をユーザーに提示 → 結果を受けてラベルを外す → `SendMessage` でレーンへ通知 |
| **引き継ぎ報告が返った** | **同じ形で次のレーンを起こす**（`name` は §5.1 の規則に従う）。レーンは 2 タスク進むと引き継いで終了する（`lane-controller.md`「2 タスク進んだら引き継いで終了する」）。**報告に書かれた「マージ許可」を次の dispatch にそのまま載せる。** フェーズが未完了なら**ゲートは実行しない** |
| レーンが完了した | 下のゲートを実行 → 次のステージへ |
| **🔴 レビューに修正を返した** | **前ラウンドの判定を受け取ってから次の依頼を送る**（2026-08-14。台帳 #174）。**PR #75 で 3 回続けて便が交差し、毎回「判定は既に送信済み」の往復が 1 つ増えた。** **修正をコミット・push したうえで sha を 1 行送り、判定を待つ。** 依頼に**測定時 HEAD を要求する**のは既に効いており、それで毎回どちらが古いかを切り分けられた —— **切り分けられることと、往復が増えないことは別である** |

### 🔴 事象が起きないことを検知する規則は、能動的な起床機構を同時に置く（群 ξ。2026-08-15 に昇格。1 行・例外）

**無応答・停止・不在を検知する規則は、受動的な通知待ちのままでは構造的に発火しない。** 検出すべき事象が「**通知が来なくなること**」だからである。**規則を書いただけでは足りず、その規則を発火させる能動的な起床機構（`Monitor` / `Bash` の `run_in_background: true` による待ちループ）を、同じ便で張って初めて規則になる。**

> **実例（2026-08-15。PR #80 / `lane-h2`）:** レーンは `e70dad1`（**13:09:59**）を最後に停止した。**team-lead が気づいたのは 15:24 で、ユーザーに指摘されてからである —— 2 時間 14 分。** **上の監督表の「1 時間以上応答が無い → 停止を疑う」は当時も在り、規則は在った。**
> **機構は規則の不在ではなく起床の設計である** —— **13:11 にレーンの idle 通知を受けて実測し「CI 待ちだろう」と判断して終わり、次に自分が動く条件を何も設定していない。** **通知待ちで構えている限り「通知が来なくなる」は検出できない。時計で起きる必要があった。結果、タイマー役がユーザーになった。**

- **欠けていたのは閾値ではなく観測の頻度である。** 本件は 1 時間の閾値を持ちながら 2 時間 14 分気づかなかった。**閾値をいくら下げても、見に行く契機が無ければ発火しない。** 手当ての `Monitor` は **10 分無進捗 / 25 分無進捗**で鳴らす
- **沈黙を成功と読まない。** 発火条件には進捗（ブランチ HEAD か ledger の mtime が動いた）だけでなく、**終端状態（PR の `MERGED:` / `CLOSED:`）も入れる。** 失敗の形を拾わないと、失敗による沈黙が成功待ちに見える
- **🔴 張ったあと、その待ち条件の判別力を測る（群 α。本群とは別の軸である）。** **機構を張ったことと、張った機構が 2 状態を区別することは別の合否である。** **判定基準: 待ち条件が**単一の信号**だけに依存していないこと** —— **進捗の信号 1 系統に加えて、生存の陽性証拠（相手が触る別のファイル・ディレクトリの mtime）と終端状態を含め、最低 2 系統にする。1 系統だけの機構は不合格。**<br>**本節を書いた便で実際に踏んだ** —— `task-reviewer` の待ちに `Monitor` を張ったが**報告ファイルの mtime 1 点しか見ておらず、報告を書き始める前の 10 分で `STALL:` が誤爆した。レビュアーは健全で、同じ scratchpad に検証用フィクスチャを 2 本書いていた**（台帳 #230）。**「まだ書き始めていない」と「死んだ」は、報告ファイルだけを見ている限り同じ観測になる**（`lane-controller.md`「対処 1」の「レポートファイルの存在を条件にしない」は**存在**の側だけを警告しており、**mtime** の側が抜けていた）

   > **失敗の機構が同じなら同じ穴、結果だけが同じなら別の穴である。** 例: 「呼ぶ側の配線が守られていない」と「`> 0` の恒真述語」は**どちらも結果は『テストが何も守っていない』だが機構が違う**ので別に数える。「起きたあと次の一手を打たなかった」3 件は機構が同じなので 1 群である。
   > **寄せ方は閾値の判定を直接変える。** 別機構を 1 群に寄せれば 1 回のものが 3 回になり、逆も起きる。**群にした根拠（どの機構が同じか）を昇格 PR に必ず書くこと。** 書けないなら、それは同じ穴ではない。

   **昇格 PR には次の 3 つを必ず書く。**

   - **なぜ**（実例と日付）—— **理由の無い規則は次のレーンが消す**（契約 §68.8 の実測）
   - **観測点**（効いたと分かる signal）—— 無いと効いたかを測れない。**issue #51 の受け入れ条件 5 がその形だった**
   - **🔴 配置先の全ロール**（群 K。2026-08-14 に追加）—— **昇格させる規則は、同じ誤りを書きうる**全ロール**へ同時に置く。置かないロールがあるなら、置かない理由を 1 行書く**<br>**なぜ: 片側にだけ置くと、もう片側は同じ誤りを書き続ける。** 群 K は PR #69 で昇格済みだが、**stage5 で 7 行に再発した**（台帳 #137 / #154 / #157 / #158 / #160 / #161 / #168。**最大のものは群 E** —— 「断定に変異を当てる」が `task-reviewer.md` にしか無く、**implementer が production の doc へ書く断定は誰の射程にも入らないまま 10 回再発した**）<br>**⚠️ この行の証拠となる台帳行は、それぞれの primary 群の下で数える。本行のために回数を二重計上しない**（寄せ方は閾値の判定を直接変える）<br>**観測点: 昇格 PR の本文に「置いたロール」と「置かなかったロールとその理由」が書かれていること**

   **昇格 PR は通常の PR レビューを通す。** PR #52 では追記が既存記述と矛盾しかけ、レビューで検出された。**定義の変更こそ差分レビューが要る。**

   **昇格 PR は、対象行の `昇格` 列を `昇格済み（PR #<n>）` に書き換えるところまでを含む。** マージ後に書こうとすると行は `—` のまま残り、**次のステージのゲートが同じ行を数えて同じ昇格 PR をもう一度作る。**

   **PR 本文・タイトル・群の表は、最後のコミットを積んだ後に取り直す。** 昇格作業は自分の後続コミットで件数と群構成が動くため、**書いた瞬間に偽になる**（PR #57 で 3 回起きた）。**PR 本文はマージ後も残る恒久記録であり、訂正の機会が乏しい。**

   **昇格した規則は台帳の `## 昇格済みの規則（棚卸し用）` にも 1 行足す。** その表は `観測点` 列を持つ —— **上で必須と定めた観測点は、PR 本文ではなくそこに書く**（PR 本文はマージ後に探しにくい）。**昇格済みの規則があるのに同じ穴が 3 回目に出たら、規則の書き方が悪い。** 追記で足さず、**その規則を書き直す** —— 既存記述と矛盾したまま足すと、次のレーンが「矛盾している」として両方消す。

   > **⚠️ 判定基準そのものが壊れていないかを、同じ場で確かめる。**
   > **そのステージでマージした PR の本数**（`gh pr list --state merged --search "merged:>=<ステージ開始日>"`）**と、台帳に増えた行数を比べる。PR が 3 本以上あって増加が 0 行なら、基準を見直す。**
   > 「うまく動いていて出ない」と「基準が壊れていて出ない」は区別が要る。**後者は空振りであり、不合格と見分けがつかない。**
   > **`定義の穴: なし` の連続回数では測れない** —— レビュー報告は短命な作業ファイルにしか無く、台帳は 0 件を記録しない設計だからである。**永続的に数えられるのは「PR 本数」と「台帳の行数」の 2 つだけである。**

   > **🔴 集計コマンド自体を、罠を持つ行に当てて検算する（群 I。2026-08-10 に実際に外した）。**
   > **`awk -F'|'` で未昇格を数えると、セル内の `\|` でも分割して列がずれ、行を静かに落とす。** 実測で **72 と出たが正解は 75**。落ちた 3 行（#58 / #84 / #99）のうち **2 行は、そのゲートが昇格させる群の構成要素そのものだった。**
   > **落ちた行は出力に現れないので、少なく出たことに気づく手段が無い。** 数える前に `grep -cE '^\| [0-9]+ \|'` で総行数を独立に取り、内訳の和と一致することを確かめる。
   > **🔴 差分を数える工程には `--no-ext-diff` を付ける**（群 T。正典は §「言明の一部だけを測って…」の末尾と `lane-controller.md`「差分を機械解析するなら…」）。**このリポジトリは `diff.external=difft` であり、`git diff <range> | grep -c '^diff --git'` は 0 を返す。**
   > **これは検証 E（3 版連続で壊れた squash 判定）と同じ機構である** —— **解析コマンドを、その解析が曖昧になる入力に当てて検算していない**（正典は `lane-controller.md`「出力を解析する検査は…」）。

   > **🔴 転記の直前に「この一覧を書いた後に起きた事象が無いか」を 1 度だけ問う（群 G）。**
   > **転記は「レビュアーの `定義の穴` 一覧を写す」運用なので、一覧を書いた時刻より後に起きたことを構造的に落とす。** stage4 で 3 回起きた —— 予告だけ書かれて実施記録が残らない（台帳 #26）/ レビューファイルが `定義の穴: なし` のまま更新されない / **レビュー完了後に起きた 2 件がどの一覧にも載らなかった**（台帳 #53）。
   > **同じ形が索引でも起きる** —— **worklist に載った章は全項目照合されたが、同じタスクを縛る `§30.2` の env 表は worklist に無かったため、誰も踏まなかった**（台帳 #97）。**訂正を 1 箇所に入れたら、同じ誤りを持つ他の手順書へ後方転記する**（台帳 #79。5 時間後に実施者へ渡す直前まで誤った手順が残っていた）。
   > **【規則】一覧・索引を正典にする運用では、「一覧の外に何があるか」を問う工程を 1 つ必ず持つ。**
