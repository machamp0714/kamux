# 規則への昇格

台帳（`.claude/AGENT-LESSONS.md`）に溜まった事象を読み、同じ失敗が繰り返されているものを `.claude/agents/*.md` や `.claude/skills/*/SKILL.md` の規則にする。

## このスキルの役割

昇格の閾値、昇格 PR に必要なもの、マージ前の人間の承認。この 3 つはここだけに書く。他のファイルにはポインタだけを置く（`CLAUDE.md` と台帳の「## 昇格」節がそうなっている）。

| | |
|---|---|
| 判断して実行する人 | team-lead 自身。lane-controller ではない |
| 読む対象 | 台帳のうち `昇格` 列が `—` の行。**この列に書ける値の語彙は台帳の「## 昇格」節が持つ。ここへ写さない** |
| 書き換える先 | `.claude/agents/*.md`、`.claude/skills/kamux-lane/SKILL.md`、このファイル |
| 扱わないもの | 仕様・型・命名・順序・値の話。これは契約変更要求で、contract-owner が裁定する |

契約はこの工程を管轄していない。契約 117 章の適用先表が、台帳と `.claude/agents/*.md` への昇格を「契約の管轄外。team-lead が決める」と明記している。だからこのスキルは契約を変更せずに人間の承認ゲートを置ける。

## 起動のしかた

2 つの経路がある。

- `kamux-lane` のステージ完了ゲートから呼ぶ。これが本来の経路で、定期的に判定するのはここだけ
- 「ステージ5 を昇格判定して」のように直接呼ぶ

どちらでも、起動したことを記録に残す。記録が無い回は実施していないものとして扱う。書き先は「記録の残しかた」を見ること。

## 台帳を数える

数える単位はステージであってフェーズではない。stage3 のように 1 ステージが M2-1 と M3-1 の 2 フェーズを含むことがある。台帳の `ステージ` 列はこの判定のためにある。

数える前に、総行数を独立に取っておく。

```bash
grep -cE '^\| [0-9]+ \|' .claude/AGENT-LESSONS.md            # 総行数
grep -cE '^\| [0-9]+ \|.*\| — \|$' .claude/AGENT-LESSONS.md  # 未昇格
```

`awk -F'|'` は使わない。セル内の `\|` でも分割して列がずれ、行を黙って落とす。落ちた行は出力に現れないので、少なく出たことに気づく手段が無い。

差分を数えるときは `--no-ext-diff` を付ける。このリポジトリは `diff.external=difft` なので、付けないと `git diff <range> | grep -c '^diff --git'` が 0 を返す。

転記する直前に、一度だけ「この一覧を書いた後に起きたことは無いか」と問う。転記はレビュアーの一覧を写す作業なので、一覧が書かれた時刻より後のできごとを構造的に落とす。

## 同じ穴かどうか

結果ではなく原因で決める。原因が同じなら同じ穴、結果だけが同じなら別の穴。

「テストが何も守っていない」という結果が同じでも、呼び出し側の配線が抜けているのと、条件式が常に真なのとでは原因が違う。別々に数える。

この分け方は件数を直接動かす。別の原因をひとつにまとめれば 1 回だったものが 3 回になるし、逆も起きる。まとめた理由を昇格 PR に書くこと。書けないなら、それは同じ穴ではない。

まとめすぎていないかは、昇格した規則の形で分かる。事象 1 行につき下位規則 1 本になっていたら、原因の違うものをひとつにしている。分けすぎのほうは、手当てが 1 本で足りるかで見る。

## 昇格するかの判断

| 状況 | どうするか |
|---|---|
| 同じ穴が 2 回以上 | 定義ファイルへ昇格させる PR を作る。1 回は偶然、2 回は構造 |
| 1 回だけ | そのまま残す。消さない |
| 初出から 3 ステージ跨いで 1 回のまま | `昇格` 列に `棄却（<理由>）` と書いて閉じる。行は消さない |
| 1 回だが、手当てを既に書いてしまった | `昇格済み（PR #<n> / 群 <X>-<k>）— 例外: 1 回。<なぜ閉じるか>` と書く。「例外」の語を必ず入れる |
| その PR のレビューで出た穴を、同じ PR で成果物を直して塞いだ | 1 回でも閉じてよい。閾値の 2 回は「まだ直していないものを定義へ上げるか」の判定なので、直したものを開けたままにする意味は無い |
| その PR の dispatch プロンプトで口頭補填しただけ | 閉じない。`—` のまま残す。dispatch はタスク 1 本で消えるので、次のタスクには何も残らない |
| 作り方ではなく作るものの話だった | `契約 §<n> として採用（PR #<m> …）` と書き、contract-owner へ契約変更要求として上げる |

「例外」の語が無い行は、次のゲートが「2 回あったのだろう」と読んで前例に使う。1 回のものを閉じるときは必ず書く。

口頭補填を「直った」に含めないこと。定義ファイルへ上がるべきものだけが消えていく。判定は単純で、`昇格済み` と書いた行が成果物の差分を指せるかどうか。dispatch に書いたことしか根拠が無い行は閉じない。

## 昇格 PR に書くこと

3 つある。

- **なぜ**。実例を添える
- **観測点**。効いたと分かる signal。無いと効果を測れない
- **配置先の全ロール**。同じ誤りを書きうるロールへ同時に置く。置かないロールがあるなら、置かない理由を 1 行書く

片側にだけ置くと、もう片側は同じ誤りを書き続ける。ロールが 1 つしかないプロジェクトでは 3 つ目は自明に満たされる。

観測点については、散文の理由よりも機械で判定できる検査のほうを優先する。理由を書いても、守る検査が無ければ次の書き手に消される（契約 70 章の裁定）。

この 3 つは PR 本文に書く。定義ファイルへ入れる規則の本文には、日付も PR 番号も台帳の行番号も書かない。実例が要るなら `references/case-studies.md` へ置いて、規則からは 1 行で指す。

定義ファイルは毎回のレーンが読む。事例を本文に溜めると、規則そのものが埋もれて読めなくなる。

## 昇格 PR の進め方

通常の PR レビューを通す。定義の変更こそ差分レビューが要る。

対象行の `昇格` 列を `昇格済み（PR #<n>）` に書き換えるところまでを、同じ PR に含める。マージ後に書こうとすると行は `—` のまま残り、次のゲートが同じ行を拾って同じ PR をもう一度作る。

閉じる台帳行の番号を、PR 本文に 1 行で宣言する。

```
閉じる台帳行: 50 187 213
```

マージ前の点検がこの行を入力に取る。書かないと点検は母数 0 で自明に通り、閉じ忘れを見つけられない。

PR 本文とタイトルと群の表は、最後のコミットを積んだ後に取り直す。昇格作業は後続のコミットで件数と群の構成が動くので、先に書くとその瞬間に嘘になる。PR 本文はマージ後も残る記録で、訂正の機会が乏しい。

昇格した規則は台帳の「## 昇格済みの規則（棚卸し用）」にも 1 行足す。その表は `観測点` 列を持っているので、観測点は PR 本文ではなくそこに書く。

昇格済みの規則があるのに同じ穴が 3 回目に出たら、規則の書き方が悪い。追記で足さず、その規則を書き直すこと。既存の記述と矛盾したまま足すと、次のレーンが両方消す。

## ユーザーの承認

🔴 昇格 PR は、レビューの承認と CI 緑を満たしても、それだけではマージしない。ユーザー本人の承認を得てからマージする。

1. 最終コミットを積み終える
2. 取り直した PR 本文を、team-lead がユーザーへ直接見せる。他のエージェントを経由しない
3. 承認をもらい、そのときの `git rev-parse HEAD` を控える
4. PR 本文へ 1 行書く。`ユーザー承認: <YYYY-MM-DD HH:MM> / 承認時の sha: <sha>`
5. `gh pr merge` を実行する

承認した sha より後にコミットが増えたら、承認を取り直す。

```bash
git diff --no-ext-diff --stat <承認sha>..HEAD   # 空でなければ手順 2 からやり直す
```

承認したのは見せた差分であって、ブランチ名ではない。

承認記録を PR 本文に置くのは、GitHub に残って `gh pr view <n> --json body` で機械判定でき、しかもコミットを増やさないから。

却下した案は、台帳のような git 管理下のファイルへ書くもの。これは上の差分検査と噛み合わない。書いた瞬間に差分が空でなくなり、再承認と記録が延々と続く。記録先を追跡ファイルへ移すなら、差分検査から承認記録のコミットを外すこと。

契約 32 章の 7 条件は上書きしない。あの章は 33 本の PR のマージ自動化を定めたもので、`needs-human-verification` ラベルが指す 7 本もその 33 本についての規則。

昇格 PR は 33 本の外にあり、`kamux-lane` の「やってはいけないこと」が定める独自の手続きの上に成り立っている。

観測点は、PR 本文に `ユーザー承認:` の行があり、そこに書かれた sha からマージ時点までの差分が空であること。

## 判断の物差しが壊れていないか

昇格の判定と同じ場で、判定基準そのものを確かめる。

そのステージでマージした PR の本数（`gh pr list --state merged --search "merged:>=<ステージ開始日>"`）と、台帳に増えた行数を比べる。PR が 3 本以上あって台帳の増加が 0 行なら、基準を見直したほうがいい。

うまく動いていて出ないのか、基準が壊れていて出ないのか。後者は空振りで、不合格と見分けがつかない。

レビュー報告の「定義の穴: なし」の連続回数では測れない。レビュー報告は短命な作業ファイルにしか無いし、台帳は 0 件を記録しない設計になっている。永続的に数えられるのは PR の本数と台帳の行数の 2 つだけ。

## 記録の残しかた

書くのは team-lead。時点は 2 つある。

- 起動した直後に、対象ステージと未昇格の行数と総行数
- 判定が終わった時点で、昇格させた群と PR 番号、棄却した行と理由。昇格 0 件ならそう書く

書き先のファイル名はここに書かない。正典は `kamux-lane` の「裁定と実施記録は、リポジトリに残る形で渡す」が持っている。この書き先は一度動いたことがあるので、写すと二重の正典になる。

ただし粒度だけはここで決める。書き先はフェーズ単位だが、このスキルの判定単位はステージ。複数フェーズを含むステージでは、マージ順で先頭のフェーズ 1 つにだけ書く。2 箇所に書くと、後から読む人がどちらを実施記録とみなすか決められない。

書き先は git 管理外なので、経緯を後から引く用途には使わない。引くときは台帳の事象行を引く。ここに書くのは「この回に何をしたか」で、後続が引用する経緯ではない。

## マージ前の点検

点検スクリプトを打つ。正典の一意性、ユーザーの承認、PR 本文の必須 3 項目、閉じる台帳行の照合。この 4 つを 1 本で見る。

```bash
# リポジトリのルートで実行する
.claude/skills/kamux-promotion/scripts/check-promotion-pr.sh \
  --pr <n> --approved-sha <承認時に控えた sha>

# 昇格 0 件の便では、照合する対象が無いので明示的に外す
.claude/skills/kamux-promotion/scripts/check-promotion-pr.sh --pr <n> --no-promotion
```

終了コードは 3 値。0 が全合格、1 が不合格、2 が引数か前提が不正で測定できていない状態。2 を 1 に丸めないこと。測れていないものを不合格と同じ扱いにすると、次に 0 が出たときそれが本物か判別できない。`SKIP` と出た行も合格ではない。

検査の中身はスクリプトが正典なので、ここには書き写さない。ただし、なぜその形でなければならないかは下に残す。スクリプトを書き換える人はここを読んでから書き換えること。

### 閉じ忘れは件数では見つからない

🔴 「起動時の未昇格数 − 閉じた行数 = 現在の未昇格数」という式で判定してはいけない。閉じた行数を PR 差分から数える限り、この式は `現在 = 起動時 − (起動時 − 現在)` に還元されて必ず成立する。閉じ忘れた行は、閉じた行数の側にも現れないので相殺される。

だから、閉じるつもりだった番号の集合を台帳の現状とは別のところ（PR 本文）から取る。

### フィルタを書いたら前後の件数を突き合わせる

宣言をパースする段にも同じ穴が開く。実在しない番号を宣言すると「台帳に `—` で無い」→「閉じた」と読まれて黙って消えるし、区切りにカンマが混ざると 1 件が数値フィルタで捨てられる。残りが 0 でなければ「母数 0 なら不合格」も発火しない。

どちらもフィルタが落としたものが出力に現れない形。フィルタを 1 本書いたら、その前後の件数を必ず突き合わせる。

### 未昇格の数は語彙で分類しない

`昇格済み` や `棄却（` のような語で分類して数えると、語彙表に無い書き方をした行が黙って漏れる。`| — |` の行末アンカーで測ること。この形だけがセル内の素の `|` に影響されない。

行数だけでは合格を出せない。セル内の `|` で表が割れても行数は返るので、総行数と対で打つ。

列数検算の正典は `scripts/check-ledger-columns.py`（素の `|` だけを数え、表ブロックごとにヘッダと突き合わせる）。`awk -F'|'` は行の分割だけでなく**列数検算にも使えない** —— escape 済み `\|` を区切りに数え、正常な行を「壊れた行」と報告する偽陽性を作る。偽の欠陥報告が 12 日間、修理対象として引き継がれた実例がある。

## 点検に落ちたとき

| 出力 | 何が起きているか | どうするか |
|---|---|---|
| `FATAL:`（終了コード 2） | 測定できていない。ルート以外で打った、`gh` が無い、PR 番号か sha が誤り | 前提を直して打ち直す。不合格の証拠にはならない |
| `NG [1]` 二重の正典 | 閾値の記述がこのファイル以外にもある | 増えた側を消してポインタに置き換える |
| `NG [1]` どこにも無い | 母数 0。検査対象の語かパスが実物とずれた | スクリプト先頭の変数を実物に合わせる。0 件を「違反なし」と読まない |
| `NG [2]` 承認行が無い | ユーザーの承認を得ていない | 「ユーザーの承認」の手順 2 へ戻る。レビュー承認と CI 緑は代わりにならない |
| `NG [2]` 承認 sha 以降に差分 | 承認後にコミットを積んだ | 承認を取り直す。本文に追記して済ませない |
| `NG [3]` | 必須 3 項目が PR 本文に無い | 足りない項目を書く。書けないなら昇格の根拠が無い |
| `NG [4]` 宣言行が無い | `閉じる台帳行:` を書いていない | 書く。昇格 0 件なら `--no-promotion` を渡す |
| `NG [4]` 数値でない token | カンマ等が混ざり、その分が照合されていない | 半角空白区切りで書き直す |
| `NG [4]` 実在しない ID | 台帳に無い行番号を宣言した | 台帳を見て直す |
| `NG [4]` 閉じ忘れ | 宣言したのに `昇格` 列が `—` のまま | 台帳の該当行を同じ PR の中で閉じる |

検査を通すために検査自身を緩めないこと。`--no-promotion` を面倒だからという理由で付けた瞬間、閉じる台帳行の照合は永久に空振りする。昇格 0 件であることを台帳の差分で確かめてから付ける。
