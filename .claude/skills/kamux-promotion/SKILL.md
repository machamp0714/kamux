# kamux 規則の昇格

`.claude/AGENT-LESSONS.md` に溜まった**事象**を、`.claude/agents/*.md` / `.claude/skills/*/SKILL.md` の**規則**へ昇格させる。

## 1. 正典宣言と適用範囲

**本ファイルが、昇格の閾値・昇格 PR の要件・人間承認ゲートの唯一の正典である。** 他のファイルへ書き写さない —— 書き写した瞬間に二重の正典になり、片方だけ直せば静かに乖離する（`CLAUDE.md` §3 と `.claude/AGENT-LESSONS.md`「## 昇格」節は、**ここへのポインタだけ**を持つ）。

| 項目 | 値 |
|---|---|
| **判定者・実行者** | **team-lead 自身。** lane-controller ではない（`lane-controller.md`「昇格の判断はあなたがしない」と対になる） |
| **入力** | `.claude/AGENT-LESSONS.md` の `昇格` 列が `—` の行 |
| **出力先** | `.claude/agents/*.md` / `.claude/skills/kamux-lane/SKILL.md` / 本ファイル |
| **射程外** | **作るものの話（仕様・型・命名・順序・値）。** これは契約変更要求であり contract-owner の専管である |

**契約はこの工程を管轄しない。** 契約 §117 の適用先表は `.claude/AGENT-LESSONS.md` / `.claude/agents/*.md` への昇格を「**契約の管轄外**（§105.5.2 / §107.7 の末尾と同じ扱い）。**team-lead が決める**」と明記している。**だから本スキルは契約ファイルを変更せずに人間承認ゲートを新設できる。**

## 2. 起動条件

| 経路 | 形 |
|---|---|
| **ステージ完了ゲート**（主経路） | `kamux-lane` の `## 6` 「ステージ完了ゲート」の確認 3 から本スキルを起動する。**ゲートが昇格の唯一の定期判定点である** |
| **明示起動** | 「ステージ5 を昇格判定して」「台帳の未昇格を見て」。引数はステージ ID |

**どちらの経路でも、起動したこと自体の実施記録を残す**（§11）。**起動記録が無い回は、未実施として扱う。**

## 3. 入力

- 台帳: `.claude/AGENT-LESSONS.md`
- 対象行: `昇格` 列が `—` の行
- **`昇格` 列に書ける値の語彙は台帳の「## 昇格」節が持つ。** ここへ写さない

**数える単位はステージであってフェーズではない**（stage3 = M2-1 ∥ M3-1 のように 1 ステージが複数フェーズを含む）。台帳の `ステージ` 列がこの判定のためにある。

## 4. 集計 —— 母数を先に取る

> **🔴 集計コマンド自体を、罠を持つ行に当てて検算する（群 I。2026-08-10 に実際に外した）。**
> **`awk -F'|'` で未昇格を数えると、セル内の `\|` でも分割して列がずれ、行を静かに落とす。** 実測で **72 と出たが正解は 75**。落ちた 3 行（#58 / #84 / #99）のうち **2 行は、そのゲートが昇格させる群の構成要素そのものだった。**
> **落ちた行は出力に現れないので、少なく出たことに気づく手段が無い。** 数える前に `grep -cE '^\| [0-9]+ \|'` で総行数を独立に取り、内訳の和と一致することを確かめる。
> **🔴 差分を数える工程には `--no-ext-diff` を付ける**（群 T。正典は `kamux-lane` SKILL.md §「言明の一部だけを測って…」の末尾と `lane-controller.md`「差分を機械解析するなら…」）。**このリポジトリは `diff.external=difft` であり、`git diff <range> | grep -c '^diff --git'` は 0 を返す。**
> **これは検証 E（3 版連続で壊れた squash 判定）と同じ機構である** —— **解析コマンドを、その解析が曖昧になる入力に当てて検算していない**（正典は `lane-controller.md`「出力を解析する検査は…」）。

> **🔴 転記の直前に「この一覧を書いた後に起きた事象が無いか」を 1 度だけ問う（群 G）。**
> **転記は「レビュアーの `定義の穴` 一覧を写す」運用なので、一覧を書いた時刻より後に起きたことを構造的に落とす。** stage4 で 3 回起きた —— 予告だけ書かれて実施記録が残らない（台帳 #26）/ レビューファイルが `定義の穴: なし` のまま更新されない / **レビュー完了後に起きた 2 件がどの一覧にも載らなかった**（台帳 #53）。
> **同じ形が索引でも起きる** —— **worklist に載った章は全項目照合されたが、同じタスクを縛る `§30.2` の env 表は worklist に無かったため、誰も踏まなかった**（台帳 #97）。**訂正を 1 箇所に入れたら、同じ誤りを持つ他の手順書へ後方転記する**（台帳 #79。5 時間後に実施者へ渡す直前まで誤った手順が残っていた）。
> **【規則】一覧・索引を正典にする運用では、「一覧の外に何があるか」を問う工程を 1 つ必ず持つ。**

## 5. 同じ穴の判定

> **⚠️「同じ穴」は結果ではなく**機構**で判定する。**
> **失敗の機構が同じなら同じ穴、結果だけが同じなら別の穴である。** 例: 「呼ぶ側の配線が守られていない」と「`> 0` の恒真述語」は**どちらも結果は『テストが何も守っていない』だが機構が違う**ので別に数える。「起きたあと次の一手を打たなかった」3 件は機構が同じなので 1 群である。
> **寄せ方は閾値の判定を直接変える。** 別機構を 1 群に寄せれば 1 回のものが 3 回になり、逆も起きる。**群にした根拠（どの機構が同じか）を昇格 PR に必ず書くこと。** 書けないなら、それは同じ穴ではない。

> **🔴 群が 1 機構かを検算する方法（PR #69 のレビュアーが示した。採用する）:**
> **昇格した規則が「台帳 1 行につき下位規則 1 本」の形になっているなら、その群は 1 機構ではない。**
> 例: 群 J の【規則 1】は #96（記録は在るが探せない）、【規則 2】は #85（記録そのものが失われた）に 1 対 1 対応していた。**結果（§32 条件 2 の根拠が引けない）は同じだが原因が違う** —— 本スキルが正典に書いた反例（「呼ぶ側の配線」と「`> 0` の恒真述語」）とまったく同じ形である。
> **この検算は寄せすぎだけを捕まえる。** 分けすぎ（同じ機構を 2 群にした）は別途、**手当てが 1 本で足りるか**で見る。

## 6. 閾値判定表

| 状況 | 動き |
|---|---|
| **同じ穴が 2 回以上** | **定義ファイルへ昇格させる PR を作る。** 1 回は偶然、2 回は構造 |
| 1 回だけ | そのまま残す（消さない） |
| **初出から 3 ステージ跨いで 1 回のまま** | `昇格` 列に `棄却（<理由>）` と書いて行を閉じる。**行は消さない** |
| **🔴 1 回だが、手当てを既に書いてしまった** | **`昇格済み（PR #<n> / 群 <X>-<k>）— 例外: 1 回。<なぜ閉じるか>` と書く。「例外」の語を必ず入れる**<br>**なぜこの行が要るか: 手当てを書いたのに `—` で残すと、次のゲートが同じ手当てをもう一度作る。かといって黙って閉じると、群を 1 機構 2 行に見せかけたのと区別が付かない**（PR #69 のレビューが群 J / 群 Q で実際に検出した）<br>**⚠️ 例外の語が無い行は、次のゲートが「2 回あったのだろう」と読んで前例に使う** |
| **その PR のレビューで出た穴を、同じ PR で**成果物の変更**で直した** | **1 回でも `昇格済み（PR #<n>）` と書いて閉じてよい。** 閾値「2 回」は「まだ直していない事象を定義へ上げるか」の判定であり、**既に直したものを開いたままにする意味は無い**（次のゲートが同じ修正をもう一度作る） |
| **🔴 その PR の dispatch プロンプトで**口頭補填**しただけ** | **閉じてはならない。`—` のまま残す。** **dispatch はタスク 1 本で消えるので、次のタスクには何も残っていない**（復元後の再ビルド / `git checkout --` の順序 / 変異の適用手段が実例）。<br>**🔴 `--no-fail-fast` はかつてここに並んでいたが、2026-08-15 の昇格 PR で群 β として `rust-implementer.md` / `task-reviewer.md` / `lane-controller.md` / `kamux-lane` SKILL.md へ入った**（台帳 #40）。**実例から外したのは「口頭補填を閉じてよくなった」からではなく、**定義側へ上がったから**である** —— **本行の主張（口頭補填では閉じない）はそのまま生きている。****口頭補填を「直った」に含めると、定義ファイルへ上がるべきものだけが消える —— 昇格の必要性が最も高い層が、最も閉じられやすい**<br>**判定: `昇格済み` と書いた行が、成果物の差分を指せること。「dispatch に書いた」しか根拠が無い行は閉じない** |
| **作り方ではなく作るものの話だった** | `契約 §<n> として採用（PR #<m> …）` と書く。**定義側で直さず contract-owner へ契約変更要求として上げる** |

## 7. 昇格 PR に必ず書く 3 つ

- **なぜ**（実例と日付）—— **理由の無い規則は次のレーンが消す**（契約 §68.8 の実測）
- **観測点**（効いたと分かる signal）—— 無いと効いたかを測れない。**issue #51 の受け入れ条件 5 がその形だった**
- **🔴 配置先の全ロール**（群 K。2026-08-14 に追加）—— **昇格させる規則は、同じ誤りを書きうる**全ロール**へ同時に置く。置かないロールがあるなら、置かない理由を 1 行書く**<br>**なぜ: 片側にだけ置くと、もう片側は同じ誤りを書き続ける。** 群 K は PR #69 で昇格済みだが、**stage5 で 7 行に再発した**（台帳 #137 / #154 / #157 / #158 / #160 / #161 / #168。**最大のものは群 E** —— 「断定に変異を当てる」が `task-reviewer.md` にしか無く、**implementer が production の doc へ書く断定は誰の射程にも入らないまま 10 回再発した**）<br>**⚠️ この行の証拠となる台帳行は、それぞれの primary 群の下で数える。本行のために回数を二重計上しない**（寄せ方は閾値の判定を直接変える）<br>**観測点: 昇格 PR の本文に「置いたロール」と「置かなかったロールとその理由」が書かれていること**

## 8. 昇格 PR の手続き

**昇格 PR は通常の PR レビューを通す。** PR #52 では追記が既存記述と矛盾しかけ、レビューで検出された。**定義の変更こそ差分レビューが要る。**

**昇格 PR は、対象行の `昇格` 列を `昇格済み（PR #<n>）` に書き換えるところまでを含む。** マージ後に書こうとすると行は `—` のまま残り、**次のステージのゲートが同じ行を数えて同じ昇格 PR をもう一度作る。**

**PR 本文・タイトル・群の表は、最後のコミットを積んだ後に取り直す。** 昇格作業は自分の後続コミットで件数と群構成が動くため、**書いた瞬間に偽になる**（PR #57 で 3 回起きた）。**PR 本文はマージ後も残る恒久記録であり、訂正の機会が乏しい。**

**昇格した規則は台帳の `## 昇格済みの規則（棚卸し用）` にも 1 行足す。** その表は `観測点` 列を持つ —— **§7 で必須と定めた観測点は、PR 本文ではなくそこに書く**（PR 本文はマージ後に探しにくい）。**昇格済みの規則があるのに同じ穴が 3 回目に出たら、規則の書き方が悪い。** 追記で足さず、**その規則を書き直す** —— 既存記述と矛盾したまま足すと、次のレーンが「矛盾している」として両方消す。

## 9. 人間承認ゲート

**昇格 PR は、`task-reviewer` のレビュー承認と CI 緑を満たしても、それだけではマージしない。** ユーザー本人の明示的な承認を得てからマージする。

| 手順 | 内容 |
|---|---|
| 1 | **最終コミットを積み終える**（§8 のとおり、本文はここより前に書かない） |
| 2 | **取り直した PR 本文を、team-lead がユーザーへ直接提示する。** 他エージェントを経由しない —— **判定者も実行者も team-lead 本人だから、中継が 1 段も要らない** |
| 3 | **ユーザーの明示的な承認を得る。** 承認の言葉と、そのときの `git rev-parse HEAD`（= 承認 sha）を控える |
| 4 | **PR 本文へ承認記録の 1 行を書く** —— `ユーザー承認: <YYYY-MM-DD HH:MM> / 承認時の sha: <sha>` |
| 5 | `gh pr merge` を実行する |

**🔴 承認 sha 以降にコミットが増えたら、承認を取り直す。**

```bash
git diff --no-ext-diff --stat <承認sha>..HEAD    # 非空なら手順 2 からやり直す
```

> **なぜ: 既存の群 δ（マージ許可を出す前に差分を測る）と同型である。** **承認したのは「見せた差分」であって「ブランチ名」ではない。** レビュー承認後にコミットが積まれてレビュー対象と実物がずれた事故は既に起きている（台帳 #16）。

> **🔴 承認記録を PR 本文に置くのは、それがコミットを生まないからである。**
> **承認記録を git 追跡ファイルへ書くと、書いた瞬間に `<承認sha>..HEAD` が非空になり、再承認 → 記録 → 再び非空、と閉じない。** PR 本文は GitHub 側の恒久記録で、`gh pr view <n> --json body` で機械判定でき、**かつコミットを 1 つも増やさない。**
> **⚠️ 将来この記録先を git 追跡ファイルへ移すなら、上の差分検査から承認記録のコミットを明示的に除外すること。** 除外しないと上のループに入る。

**🔴 契約 §32 の 7 条件は上書きしない。上書きの必要が無い。**

> **§32 は「33 本の PR」のマージ自動化を定めた章であり、`needs-human-verification` ラベル（§32.5）が指す 7 本も §27.4 の 33 本についての規則である**（契約 §55.2 が「7 本は増やさない」を裁定済み）。**昇格 PR はその 33 本の外にあり、`kamux-lane` SKILL.md §7 が定める「team-lead が書いて `task-reviewer` のレビューを 1 回通す」という独自手続きの上に成り立っている。**
> **だから本ゲートはラベル運用へ相乗りせず、本スキルの中だけで完結する。** 契約 §117 の適用先表が昇格を「契約の管轄外。team-lead が決める」と置いているのが根拠である（§1）。

**観測点: 昇格 PR の本文に `ユーザー承認:` の行が在り、そこに書かれた sha からマージ時の tip までの差分が空であること。**

## 10. 判定基準そのものの健全性検査

> **⚠️ 判定基準そのものが壊れていないかを、同じ場で確かめる。**
> **そのステージでマージした PR の本数**（`gh pr list --state merged --search "merged:>=<ステージ開始日>"`）**と、台帳に増えた行数を比べる。PR が 3 本以上あって増加が 0 行なら、基準を見直す。**
> 「うまく動いていて出ない」と「基準が壊れていて出ない」は区別が要る。**後者は空振りであり、不合格と見分けがつかない。**
> **`定義の穴: なし` の連続回数では測れない** —— レビュー報告は短命な作業ファイルにしか無く、台帳は 0 件を記録しない設計だからである。**永続的に数えられるのは「PR 本数」と「台帳の行数」の 2 つだけである。**

## 11. 実施記録の書き先

**書き手は team-lead、時点は 2 つ**（群 ι「工程を定義したら、産物の書き先・書き手・時点を同じ場所に書く」）。

| 時点 | 残す内容 |
|---|---|
| **本スキルを起動した直後** | 対象ステージ / 未昇格の行数 / 総行数の独立検算値（§4） |
| **判定が終わった時点** | 昇格させた群と PR 番号 / 棄却した行と理由 / **昇格 0 件ならそう書く** |

**🔴 書き先のファイル名を本ファイルへ写さない。正典は `.claude/skills/kamux-lane/SKILL.md`「裁定と実施記録は、リポジトリに残る形で渡す」節が持つ。**

> **なぜ: この書き先は 2026-08-16 に一度動いた**（`TEAM-LEAD-RULINGS.md` → `progress.md`「## 裁定」。issue #90 / PR #92）。**写せば二重の正典になり、次に動いたとき片方だけが直る**（群 λ「原本が在る値を手で写さない」/ 台帳 #4「二重の正典を 1 ファイルから削った同じコミットで、同じ閾値が別ファイルに新設された」）。
> **⚠️ その書き先は git 管理外である。恒久的な引用先には使わない** —— 経緯を後から引くときは `.claude/AGENT-LESSONS.md` の事象行を引く（同節の規律）。**本スキルが書くのは「この回に何を実施したか」であって、後続が引用する経緯ではない。**

## 12. 本スキル自身の観測点

昇格 PR をマージする前に、この 4 つを打つ。

```bash
# 1. 閾値・手続きを書いたファイルが本ファイル 1 つだけであること
#    🔴 --exclude-dir=worktrees が要る。.claude/worktrees/ には他レーンの SKILL.md の複製が在り、
#       付けないと本作業が完璧でも 2 件以上を返す（母数を数えていない検査は不合格と見分けがつかない）
grep -rl '同じ穴が 2 回以上' .claude --exclude-dir=worktrees   # → .claude/skills/kamux-promotion/SKILL.md のみ

# 2. 人間承認ゲートを通ったこと（§9）
gh pr view <n> --json body -q .body | grep -c 'ユーザー承認:'   # → 1 以上
git diff --no-ext-diff --stat <承認sha>..HEAD                   # → 空

# 3. §7 の 3 項目が PR 本文に揃っていること
gh pr view <n> --json body -q .body | grep -cE 'なぜ|観測点|置いたロール|置かなかったロール'

# 4. 台帳側が閉じたこと（同じ PR の中で）
grep -c '^| [0-9]* |.*| — |$' .claude/AGENT-LESSONS.md   # → 起動時の未昇格数から昇格分だけ減っている
```

**🔴 検査 1 と 4 は、先に母数を取ってから判定する。** 検査 1 は移設前に打って **1 件**（`kamux-lane/SKILL.md`）であることを確かめてから移設する。**1 でなければ、測っているものが想定と違う。** 検査 4 は §4 の総行数の独立検算と対で打つ —— **セル内の素の `|` で表が割れても行数は返るので、行数だけでは合格を出せない。**
