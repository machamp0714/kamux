# 実例

`SKILL.md` の規則を裏付けた実例。出典はすべて kamux（2026 年 8 月）。

規則の射程を判断するとき、または規則を消してよいか迷ったときに読む。普段は開かなくてよい。

## 理由を書いても、守る検査が無ければ消される

契約 68 章が「コンパイルが通る欠陥は、なぜ危険かを書かないと次に消される」と書いた。70 章がそれを訂正している。

> §68.8 に「コンパイルが通る欠陥は、なぜ危険かを書かないと次に消される」と書いたが、それでは足りなかった。なぜ危険かを書いても、守るテストが無ければ次に消される。
> （`00-contracts.md:8108`）

71 章も同じ裁定を再確認している（`:8301`）。実測がこうなので、規則の耐久性は散文の理由ではなく機械で判定できる検査が担保する。

このスキル自身がその実例になった。2026-08-16、`SKILL.md` に書いた「理由の無い規則は次のレーンが消す（契約 §68.8 の実測）」という引用は、章番号が違い、対象がコードであって規則ではなく、しかも原典が「それでは足りなかった」と訂正済みだった。この誤りはレビュー 4 ラウンドを生き延びた。同じ期間に、機械で判定する検査のほうは 5 回叩かれて実際に直っている。

## 事例を本文に溜めると規則が埋もれる

`kamux-promotion/SKILL.md` は 201 行まで膨らんだ時点で、🔴 が 21 個、太字が 180 箇所、日付が 8 件、章番号参照が 40 個あった。ほぼ全行が太字で、強調が強調として機能していない。`kamux-lane/SKILL.md`（583 行）と `lane-controller.md`（855 行）はもっとひどく、🔴 がそれぞれ 62 個と 66 個ある。

原因は単調増加。レビューのたびに見落とされた箇所へ強調と実例が足されるが、誰も外さない。

これを許していた記述が `CLAUDE.md` にあった。「昇格させた規則には、なぜそうするかと、効いたと分かる観測点を必ず併記する」。2026-08-17 に削除し、`SKILL.md`「昇格 PR に書くこと」へ「定義ファイルの本文には日付も PR 番号も台帳の行番号も書かない」を置いた。観測点の要求そのものは同じ節が持っている。

## 昇格の効果は測られていない

2026-08-16 時点の実測。

```
昇格済みの規則:        49 件
効果が実測された記録:   1 件（台帳 #204。台帳自身が「1 件目の記録」と書いている）
書き直しになった規則:  11 件（22%）
```

台帳 #54 は逆向きの記録で、「この保護が効いているかを測れない」と書いてある。CI が対象ディレクトリを持たないため。

## 昇格 PR が契約 32 章の外にある根拠

契約 32 章は 33 本の PR のマージ自動化を定めた章で、`needs-human-verification` ラベルが指す 7 本も 27 章 4 節の 33 本についての規則。契約 55 章 2 節が「7 本は増やさない」を明示的に裁定している（カテゴリ 6 を素直に流すと 7 本が 20 本以上に膨れ、32 章冒頭の趣旨が消えるため）。

昇格が契約の管轄外であることは、契約 117 章の適用先表が「契約の管轄外（105 章 5 節 2 項 / 107 章 7 節の末尾と同じ扱い）。team-lead が決める」と書いている。

## 集計コマンドが行を黙って落とす

2026-08-10、`awk -F'|'` で未昇格を数えたところ 72 と出たが、正解は 75 だった。セル内の `\|` でも分割して列がずれ、3 行が落ちた。落ちた 3 行のうち 2 行は、そのゲートが昇格させる群の構成要素そのものだった。

落ちた行は出力に現れないので、少なく出たことに気づく手段が無い。

同じ形が語彙による分類でも起きる。2026-08-16、231 行を `昇格済み` / `棄却（` / `契約 §<n> として採用` / `—` の 4 分類で数えたところ、和が 229 にしかならなかった。漏れた 2 行は、1 つが語彙表に無い自由記述、もう 1 つが `契約 §128.5 として採用` で章番号が `<n>.<m>` の形だったため `§[0-9]+ として採用` に掛からなかった。

## PR 本文を先に書くと嘘になる

PR #57 で 3 回起きた。昇格作業は後続のコミットで件数と群の構成が動く。

## 口頭補填では閉じない

dispatch プロンプトで補った内容はタスク 1 本で消える。復元後の再ビルド、`git checkout --` の順序、変異の適用手段が実例。

`--no-fail-fast` はかつてこの実例に並んでいたが、2026-08-15 の昇格 PR で群 β として `rust-implementer.md` / `task-reviewer.md` / `lane-controller.md` / `kamux-lane/SKILL.md` へ入った（台帳 #40）。実例から外したのは口頭補填を閉じてよくなったからではなく、定義側へ上がったから。

## 承認後にコミットが積まれる

2026-08-14、レビューの承認は `df5d06f` に対して出たが、マージされたのは `0934abf` で `df5d06f..95fd6fe`（3 ファイル / +8 行）を含んでいた（台帳 #176）。PR 本文に「承認後に 1 コミット積んだ」と書いたが、それは口頭補填であって手当てではない。

同じ形の 1 件目は台帳 #16。全差分レビューのパッケージ生成後にコミットが積まれた。

レビュー依頼中にコミットを積まない規律はまだ定義に無い。台帳 #220 が PR #78 で 4 回、#232 が本スキルの PR で 5 回目を記録している。どちらも未昇格。

## 閉じ忘れは件数では見つからない

2026-08-16 のレビューが実測した。台帳 #50 / #187 / #213 を 1 群として昇格させ、実装が #213 だけ閉じ忘れて `—` のまま残す形を作ったところ、`20 − 2 = 18 = 現在の未昇格数` が成立して合格を返した。

## パース段にも同じ穴が開く

同日のレビューが 2 形を実測した。

- 実在しない番号（`50 187 999999`）を宣言すると、台帳に無い `999999` は「`—` に一致しない」→「閉じた」へ吸収され、警告なく差集合から消えた
- 区切りにカンマが混ざる（`50 187, 213`）と `187,` が数値フィルタで捨てられ、3 件宣言したのに 2 件しか照合されなかった。残り 2 件が非 0 なので「母数 0 なら不合格」も発火しない

## 差分の grep が静かに 0 を返す

このリポジトリは `diff.external=difft` なので、`git diff <range> | grep -c '^diff --git'` は 0 を返す。`--no-ext-diff` を付けないと、差分を数える工程が全部空振りする。
