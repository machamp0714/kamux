# 実例（web-implementer）

`.claude/agents/web-implementer.md` の規則を裏付けた実例。出典はすべて kamux（2026 年 8 月）。

規則の射程を判断するとき、または規則を消してよいか迷ったときに読む。普段は開かなくてよい。

## brief が正典ではない

2026-08-05 の実測で、brief 側の欠陥を 7 件踏んでいる。enum の末尾欠落 4 件、shutdown ゲートの位置、テスト指定の欠落、起動フェーズの構造。

うまくいったのは implementer が自分で契約を読んで直したケースである。M2-1 の implementer は、brief の型定義ブロックに `StateReason` が 12 個しか無いことに気づいた。契約 §8 と brief の Interfaces 節は「13」と明記していた。契約 585 行を逐語で確認して補完し、BLOCKED にせず進めた。

件数の比較が当てにならない実例もある。計画と契約で整形スタイルが違い、1 行へ詰めた宣言を過小に数えて、契約 §8 を 13 ではなく 7 と数えた。だから照合はメンバ名の集合で行う（契約 §68.3）。

brief のコード片が実物と食い違う形も出ている。先行フェーズが関数を分解したために、後続 brief の前提が消えていた。

## 報告に書いたテストが実ファイルに無かった

「テストを追加した」と報告したが、実ファイルには無かった事例がある。だから報告に書く前に `grep` で確認する。

## 同じ型の値を取り違える

`invalidateFitCache(sid)` の `sid`（= `surfaceId(sessionId, 'editor')`）と `sessionId` は導出関係にあり、取り違えたコードを読んでも気づかない。実際に vitest 444 本を丸ごと生き延びた。

対照的に `resizePty(sid, cols, rows)` の `cols`/`rows` は同じ型が 2 本並ぶが、名前で判別できるので該当しない。

## 呼ぶ側の配線が無検査だった

台帳 #17。ストア action の呼び出しを差し替える変異が、全テスト緑を生き延びた。

台帳 #46。リファクタで観測点を切り出すと、切り出し元と切り出し先の継ぎ目が無検査のまま残る。

## 変異の復元が作業を丸ごと消した

2026-08-08、M2-3 Task 2 の implementer が踏み、Task 2 の作業が全部消えた（再実装で復旧）。

当時の定義ファイルは「変異は必ず戻す。`git checkout -- <file>` のあと `git status --short` が空であることを確認」とだけ書いており、**未コミット状態で実行すれば作業ごと `HEAD` へ巻き戻る**ことを書いていなかった。

レビュー指摘への追加修正をコミットせずに変異へ進んで消した例が 2 回ある（台帳 #43 / #104）。

## 恒真述語が 1 往復してから消える

台帳 #61。「何でも通る境界」を assert に書かない規則は 2026-08-07 に `task-reviewer.md` へ昇格したが、打つ側には無かった。そのため implementer が書いた恒真述語は、レビューで指摘されてから消える形になっていた。

期待値を production の定数から再導出する形は `ACCEPT_ERROR_BACKOFF_*` と `HOOK_EVENTS` で実測した。定数を動かすと期待値も一緒に動き、検証が黙って消える。

## 断定が変異を素通りする

旧版の規則は恒真述語と期待値の再導出だけを射程にしていたため、`doc` コメント・テスト名・production のコメントへ書く断定が素通りした。PR #74 だけで 6 例出ており、うち 3 例は「前の穴を閉じるために書いた修正差分」が持ち込んだものである（台帳 #157 / #158 / #160 / #168）。

| 例 | 断定 | 実測 |
|---|---|---|
| テスト名 `… and never polls` + `HooksStatusPanel` の doc「定期リフレッシュはしない」 | ポーリングしない | `setInterval(…, 1000)` を注入して 669 全緑 |
| 修正で書き足したコメントが「なぜ拾わないか」を逐語で主張 | 理由が成立している | その理由を偽にする変異を誰も打っていない |
| 実装者の report の測定表と、production コメントへ書いた例示 | 同じことを言っている | 食い違っていた（台帳 #160） |

実測されていない「設計上の不可能性」も断定である（台帳 #47 / #133 / #167）。

## difft が diff の grep を壊す

このリポジトリは `diff.external=difft` なので、`git diff` は 2 カラムの表を描く。stage5 で 4 回起きており、うち 1 回は team-lead が「差分は無い」と誤判定した（台帳 #127 / #131 / #152 / #159）。

2 箇所同時に打ったとき、片方が無言で不適用でも「非空」は成立する（台帳 #138）。修正が既存ブロックを複製して、一意だったアンカーが 2 箇所・6 箇所に増え、変異が無言で別のテストへ当たった例もある（台帳 #141）。

台帳 #195 は別形。`cd <サブディレクトリ> && … && git diff -- <repo 相対パス>` はパススペックが cwd 相対に解決されるため、変異が適用済みでも空を返す。`--no-ext-diff` を付けていても起きる。「変異した行を目で見る」という観測点は、出力自体が空なので射程外だった。

## dispatch と定義ファイルの優先順位が書かれていなかった

stage5 で 4 回（台帳 #135 / #139 / #153 / #163）。PR #74 では 10 本のレビューのうち 1 本だけが別の解釈を採った。受け手ごとに解釈が割れ、割れたことは割れた後でなければ分からない。

## 規則を書いた本人が同じ便でその規則を破る

stage5 で 5 回（台帳 #124 / #125 / #128 / #142 / #144）。実装ロール側の形は #144 で、「測っていない主張をコメントに書いた」という指摘への修正の中で、その修正自身が測っていない主張を新しく書いた。

台帳 #196 / #201。群 U は 5 つの定義ファイル全部に在るのに、2026-08-14 に両側で同日再発した。#196 は実装者が自分の報告 `:144` に記録した罠を次の便で踏んだ形で、その行自身が逐語で「警告文では閉じない。手当てはコマンドの形でなければならない」と書いている。

## マーカの後に作業を続けた

stage4 で 4 回。`STATUS: …` の行を書いたあとに作業を続けて実害が出た。dispatch に禁止を逐語で書いたうえで起きているので、規律ではなく順序の問題である。

## 報告ファイルに版が残らない

台帳 #56 / #67。報告ファイルは git 管理外なので、記述が偽になった時点を事後に切り分けられない。#56 は実行していない検証の出力が報告に書かれた形で、`REPORT_WRITTEN_AT` では防げない。
