# lane-controller: フェーズ完了・E2E 仕分け・人間ゲート（詳細）

`lane-controller.md` の層2 ファイルである。フェーズ完了時、E2E とスモークの仕分け、人間検証 PR の作成、実行順が特殊なフェーズ、人間ゲートの局面で読む。読んだら ledger へ `参照: lane-controller-completion.md（<局面>）` の 1 行を記帳する。章表記の分界は本体「章の書き方」に従う。

## フェーズ完了時の手順

対象者と順序の規則（全ブランチレビューはマージの前）は本体「フェーズ完了時」が持つ。手順は次の 6 つ。

1. 最後の PR を open にしたまま、全ブランチレビューを `opus` で 1 回だけ実施する（`superpowers:requesting-code-review` の code-reviewer）
2. 指摘があれば修正 implementer を 1 体だけ起動し、まとめて直す（指摘ごとに 1 体起動しない）。修正は最後の PR のブランチへ積む
3. 修正を積んだら、必ず再レビューを 1 回通してから手順 4 へ進む。手順 2 は `<承認 sha>..HEAD` を構造的に非空にするので、そのままマージすると `kamux-lane/SKILL.md`「検査と是正の順序」の規則 1（非空ならレビューへ戻す）に必ず当たる。例外にはしない。
   根拠は契約 101 章 4 節である。同節は「条件 3 の取り直しが要るのはコンフリクト解決が発生したときだけ」と定め、その理由を「解決結果は誰もレビューしていない著作物であり、条件 3 の射程そのものである」と書いている。全ブランチレビューの指摘を直した差分は、まさに「誰もレビューしていない著作物」であり、同じ射程に入る。
   32 章の条件 3 の逐語は「PR の差分全体に対して 1 回」であり、承認対象の sha を名指ししていない。「1 回」を「一度通せば以後は不要」と読むと本手順は成り立たない。成り立たせているのは 101 章 4 節の原理（レビュアーが見る差分が変わったかどうか）のほうである。再レビューが `APPROVED` を返した sha が、次の測定の起点になる
4. そのうえで最後の PR をマージする（32 章の 7 条件）
5. マージ後に見つかった穴は、あなたの手では台帳へ入らない。完了報告の `定義の穴 / 台帳へ足す行:` 欄に書いて team-lead へ渡す。手順 1〜3 で見つかった分も同じ欄に書く。本体のマージ前転記の指示は「PR 単位レビューの報告」を転記元に限定しており、全ブランチレビューの `定義の穴` はどちらの経路にも乗らない。転記路がマージと同時に閉じる形である
6. 完了報告を team-lead に返す。報告に含めるもの:

```
フェーズ: M?-?
ブランチ / worktree:
完了タスク: N / M
コミット範囲: <base7>..<head7>
テスト: cargo test —— NN passed / npx vitest run —— NN passed / npx tsc --noEmit —— OK / npm run lint —— OK / npm run fmt:check —— OK
E2E に移した項目 / 手動に残した項目: （契約 §26.5-3。手動に残した各項目が §26.4 のどのカテゴリか）
持ち越した指摘（Minor / parked）:
契約への追記要求（未処理があれば）:
人間ゲート待ち（あれば）:
定義の穴 / 台帳へ足す行: （無ければ「なし」と書く。マージ後に見つかった分もここに書く）
```

差分やコード全文を報告に貼らない。

## E2E とスモークの仕分け（フェーズ完了前に必ず行う）

契約 26 章により、フロント単体 E2E（Playwright + IPC モック、`e2e/*.spec.ts`）を採用している。基盤は M1-2 Task 17 が作る。

M1-3 以降のフェーズは、自分の計画にある手動スモークチェックリストを完了前に仕分けること。

1. DOM 操作で検証できる項目 → `e2e/<フェーズ名>.spec.ts` に spec を追加する（web-implementer に投げる）
2. 下の「人間にしかできない検証」の 5 カテゴリ（契約 26 章 4 節）に当たる項目 → 手動に残す
3. 手動に残す判断には、5 カテゴリのどれに当たるかを必ず書く。「面倒だから」は理由にならない
4. 仕分けの結果を完了報告に「E2E に移した項目 / 手動に残した項目」として明記する

E2E はユニットテストの代替ではない。純関数に切り出せるロジックは従来どおり vitest / cargo test で検証し、E2E に書くのは DOM とライブラリを跨ぐ経路だけにする。

## 人間にしかできない検証（BLOCKED として team-lead に上げる）

implementer が BLOCKED を返す前に、あなた自身が計画を読んだ時点で気づいたら先に上げてよい。

| フェーズ | 内容 |
|---|---|
| M1-4 | ビルドした `.app` を Finder からダブルクリックして PATH 解決を確認（`npm run tauri dev` では再現しない。契約 18 章）／Task 12: shim ディレクトリが rc 通過後も PATH に残るか（30 章 3 節、26 章 4 節の 5） |
| M2-2 | 実 PTY の対話モードで `Notification` / `PermissionRequest` の payload をキャプチャ。hook の stdout がターミナル表示を汚さないか実測 |
| M2-3 | 通知のクリック応答を実機で確認（`notify-rust` を選んだ唯一の理由） |
| M3-2 | `Cmd+D` / `Cmd+[` / `Cmd+]` が WebView に奪われないか実機確認 |
| M3-4 | 起動 1 秒未満 / セッション 5 個で 300MB 未満 / アイドル CPU の実測（Task 15）／Task 20: `Cmd+W` が macOS 既定メニューの Close Window に奪われないか（29 章 8 節） |

「たぶん通る」で ✅ にしない。headless で再現しない項目を通ったことにするのが、この計画で最も危険な失敗である。

## 人間による動作検証が必要な PR（契約 32 章 5 節）

対象は PR 12 / 17 / 19 / 20 / 26 / 32 / 33 の 7 本だけ。作成時に次の 2 つを行う。

1. `gh pr create --label needs-human-verification`（ラベルが無ければ `gh label create needs-human-verification --color B60205 --description "マージ前に実機での動作検証が必要"`）
2. PR 本文の末尾に検証セクションを入れる（手順 / 期待結果 / 自動化できない理由を契約 §26.4 のカテゴリ番号で示す）

そのうえで BLOCKED として team-lead に上げる。人間の確認が返ってラベルが外れるまで、その PR はマージしない。

この 7 本以外にラベルを付けてはならない。「念のため見てほしい」は理由にならない。26 章 4 節のカテゴリで説明できない検証は E2E に落とすべきものである。

## 実行順が特殊なフェーズ（契約 27 章 3 節・27 章 4 節の例外 3）

M1-1 は Task 19 → Task 20 → Task 1 → … → Task 18 の順に実行する。lint と CI は他のすべての PR が乗る土台なので先に入れる。番号を末尾にしたのは既存の相互参照を壊さないため。タスク番号は文書上の ID であって実行順ではない。

M3-4 は Task 1〜14 → 16〜21 → 15 の順に実行する。Task 15 は「ベースライン計測と要件 1〜10 の最終スモーク」であり、プロジェクト全体を締める。29 章・30 章のスクラッチと shim をその後ろに置くと、未検証の 6 タスクが最終検証の後になる。
