# 定義ファイルの書き直し（issue #94）の道具と手順

`.claude/` の定義ファイルを `kamux-promotion/SKILL.md` と同じ書き方へ揃える作業で使う。
**規則の内容は変えない。書き方だけを変える。落ちた規則が 1 つでもあれば不合格。**

対象と順序: `contract-owner.md`（済） → `web-implementer.md`（済） → `rust-implementer.md` → `task-reviewer.md` → `kamux-lane/SKILL.md`

## 道具

| | 何を測るか |
|---|---|
| `check-rewrite.py` | 受け入れ条件（🔴 / 日付 / 台帳 # / 200 文字 / § / 太字 / 見出しの参照 / code fence / 守る逐語） |
| `check-survival.py` | 旧版の文が新版か退避先に痕跡を残しているか |

```bash
python3 .claude/scripts/check-rewrite.py . <定義ファイル> <退避先> \
  --chapters=<件数>:<ダイジェスト> [--renamed=<件数>:<ダイジェスト>] \
  [--anchor=<逐語> ...] [--no-anchors] [--no-fence] [--no-chapters] [--no-decorated]

python3 .claude/scripts/check-survival.py . <定義ファイル> <退避先> [--base=<ref>] [--new=<ref>]
```

誤った引数は FATAL になり、`--chapters` は正しいコマンド全体を印字する。**散文に書いた再現コマンドは器が変わるたびに古くなるので、器の出力を貼ること。**

## 🔴 「全合格」は欠落 0 件の根拠にならない

`check-rewrite.py` は見出しと code fence と手書きアンカーしか見ない。**見出しと見出しの間の散文が 1 本消えても全検査が緑になる。**
欠落の唯一の根拠は人手の突き合わせ台帳である。

## 母数の検算は 4 本立て

それぞれ出ないものが違う。1 本では足りない。

| 検査 | 出ないもの |
|---|---|
| ラベル列の機械導出 | 内容の欠落（形式しか見ない） |
| 補集合（台帳が指さない行の機械列挙） | 引かれた行の中の、分解されなかった節 |
| 弁別トークン（識別子・API 名・ファイル名・`\d+ ?(件|本|回|箇所|行)`） | 具体値を持たない散文 |
| 文単位の生存検査（`check-survival.py`） | 意味が変わった書き換え |

**PR #95 / #96 で出た規範項目の欠落 3 件は、すべて「台帳の粒度が行」に由来する。** 行を引いていれば行の中の節が落ちても補集合に出ない。

**ラベル列を機械導出するときは code span を退避させてから分割する。** 素の `split('|')` では割れる。行数は正しい数を返すので、行数検算だけでは気づけない。

## 判定の物差し —— これが検査の本数より重要

> **読者の行動を変える文か。** 変えるなら規範項目（規則本体でも、理由でも、帰結でも、観測点でも）。変えないなら経緯・メタ。

- **候補文が乗っている行の台帳項目が `削除` / `退避` でも、その分類を文へ継承しない**
- **判定して外した候補は、件数と理由を書く。** PR #96 の欠落 3 件目は、検査は候補として出していたのに「確信度が低い」として外され、外したことが記録されなかったため誰にも見えなかった
- **🔴 文末の様相（命令形・義務表現）で絞ってはいけない。** PR #95 / #96 で落ちた 3 件はいずれも帰結・理由を述べる文だった。**欠落は規則本体ではなく、いつも理由・帰結の側で起きている**

## 書き方の型

- 見出しから `🔴`・群ラベル・日付・太字を外す。**見出しのコアが変わったら `--renamed=` で宣言する**（意図的な改名はありうるが、件数だけでは「1 本直して 1 本消す」が素通りする）
- 実測・台帳の行番号・章番号の羅列は `.claude/references/<名前>-cases.md` へ退避し、本文からは末尾 1 行で指す
- 退避先は `.claude/agents/` の**外**に置く（`.claude/agents/**` が走査対象になりうる）
- 🔴 は 1 ファイル 3 個まで（実績は 2 個）
- **`§` の分界は用途で決まる。組版ではない。** 章を値として書き込むなら `§25`、場所として名指すだけなら「25 章」。書き込む先は production のコメント・テスト名・コミットメッセージ・レポートファイル・`SendMessage` の本文・BLOCKED の理由・契約変更要求
- frontmatter（`name:` / `model:` / `tools:` / `description`）も母数に入れる。`color:` は装飾なので明示的に除外すると宣言する

## レビュー

2 体を独立に立てる。**変異は指定しない**（全件レビュアーが設計する）。**実装を揃えない** —— 同じ道具を 2 者で使えば一致は独立の裏付けにならない。

依頼に必ず入れるもの:

- 対象 tip の完全な sha。**`git rev-parse HEAD` の出力をそのまま貼り、`git cat-file -t` で解決も確認する。** `--short` の出力から残りを作らない
- 突き合わせ台帳のパスと母数の宣言
- **退避項目を弁別トークンで全件照合してほしい**
- 変異は隔離ツリーで打つ（`git worktree add --detach`）。共有ツリーに入らない
- 観測を引用するときは測定時の sha を添える
- 判定は `SendMessage` で返す（地の文は届かない）

**判定が返るまで作業ツリーも器も触らない。** PR #95 では 12 回動かしてラウンドが 6 に伸びた。

**承認は blob で固定する**（`git rev-parse <sha>:<path>`）。tip が動いても、承認の対象が何だったかは blob で一意に決まる。

## 引き継ぎ時に注意すること

- **台帳（`AGENT-LESSONS.md`）に行番号で他ファイルを指した行がある。** `task-reviewer.md:212` / `:269` / `:293`、`lane-controller.md:263`。**4 本目でそのファイルを書き直すと全部ずれるので、同じ差分で節名参照へ張り替える**
- 台帳 `#136` の `rust-implementer.md:108` は**当時の行を指す履歴の記録**なので直さない（過去の測定として真）
