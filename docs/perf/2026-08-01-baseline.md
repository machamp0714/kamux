## 🔴 実施者へ —— 計測を始める前に必ず読む 3 点

### 1. 実施はメインの作業ツリーで行うこと

**実施はメインの作業ツリー `/Users/ooidetatsuya/repo/kamux` で行うこと。** `.claude/worktrees/` 配下の複製は本ファイルの更新を反映していない場合があり、そこから測ると旧手順（`measure-perf.sh all` を素で叩くもの）で完走してしまうおそれがある。

### 2. `KAMUX_APP_PATH` を必ず渡すこと。既定のパスはこのリポジトリに存在しない

`scripts/measure-perf.sh` の既定は `src-tauri/target/release/bundle/macos/kamux.app` だが、**このリポジトリはルートが cargo workspace なので `target` はリポジトリのルートに在り、`src-tauri/target` は存在しない**（lane-controller が実測）。既定のまま打つと必ず「アプリバンドルがありません」で FAIL する（黙って PASS はしない）。

```bash
export KAMUX_APP_PATH=/Users/ooidetatsuya/repo/kamux/target/release/bundle/macos/kamux.app
```

### 3. 🔴 `measure-perf.sh all` を使わないこと。3 つを**この順で別々に**打つ

`all` は `startup` → `memory` → `idle-cpu` の順に走るが、**`startup` は先頭で `pkill -x kamux` を打ってアプリを一度終了させ、新しく起動し直す**（`scripts/measure-perf.sh:214` の逐語）。**したがって、セッション 5 個を開始して表示した状態を作ってから `all` を打つと、その状態は `startup` の時点で壊れ、`memory` と `idle-cpu` は「セッション 0 個のまっさらな起動直後」を測る。** 数字は不当に良く出て、**しかも FAIL にならない**（黙った偽の合格になる）。

正しい順序:

```bash
# (1) 起動時間。アプリは自動で終了・再起動される。セッションの準備はまだ不要
bash scripts/measure-perf.sh startup

# (2) ここで手を動かす: セッションを 5 個作成し、すべて開始してターミナル画面に表示し、
#     5 個すべてが 🟢 か ⚪ になるまで待つ。他の WebKit アプリは全部終了しておく。
#     そのうえで、出力が止まってから 30 秒以上待つ（契約 §104.3。「操作しない」だけでは
#     足りない。claude が出力し続けている最中に (3) を打つと不当に悪い値が出る）

# (3) メモリとアイドル CPU。実行中はマウス・キーボードに触らない（合計 60 秒強かかる）
bash scripts/measure-perf.sh memory
bash scripts/measure-perf.sh idle-cpu
```

`memory` と `idle-cpu` は**アプリが起動していないと FAIL する**（`kamux が起動していません`）。**しかし (2)（セッション 5 個の作成・表示）が済んだかどうかは機械では検出できない。** スクリプトはセッション数を見る経路を 1 本も持たない（`grep -ic 'session\|app\.db\|sqlite' scripts/measure-perf.sh` = 0）。(2) を飛ばして (3) に進んでも FAIL にならず、セッション 0 個の不当に良い数字で PASS してしまう。

**したがって、(3) に入る前に次の 2 点を自分で確認すること**（自動の検出は無い）:

1. 5 個すべてが表示され 🟢 か ⚪ になっていることを目で見る。
2. `memory` を実行したら、その出力の `INFO  参考値 1: kamux ツリー（PTY 込み…）` と `INFO  参考値 2: kamux ツリー − PTY 子孫（同上）` の 2 行を見比べる。PTY 子孫（`claude` / `nvim` / シェル）が 1 本でも居れば、その分だけ参考値 1 は参考値 2 より**厳密に大きい**値になる（`descendants` / `non_pty_pids` の実装上、PTY 子孫が 0 本なら 2 つの値は完全に一致する。合成 ps テーブルでの検証結果は post-approval-fix-report.md 参照）。**この 2 つの値が一致していれば、PTY 子孫が 1 本も居らず (2) が効いていない。** その場合は (2) からやり直すこと。

## 計測条件の数え方（契約 §104 の正典。別の数え方をしないこと）

- メモリは **4 プロセスの RSS の総和**（kamux 本体 + `com.apple.WebKit.WebContent` + `com.apple.WebKit.GPU` + `com.apple.WebKit.Networking`）である（契約 §104.2）。
- **PTY 子孫**（`claude` / `nvim` / シェルとその子孫）は上の総和に**含めない**。ただし子孫を含めた合計値も**参考値として必ず併記する**（契約 §104.2）。
- 対応づけは**起動時刻**で行う。**`ppid` では辿れない**（WebKit ヘルパは `ppid = 1` が既定である）（契約 §104.2 / 実測 3）。
- アイドル CPU は **60 秒平均 < 1.0% かつ最大サンプル < 5.0%**。測り方は `top -l 61 -s 1`、**1 ブロック目を捨てて 2〜61 ブロック目を使う**（契約 §104.3）。

**S-19 の前提確認（実施者が最初に 1 回だけ行うこと。コマンドと期待は第1部 §1.5:259-262 の逐語）**:

`is_scratch` 列は schema_version 3 で入る。**本ブランチのアプリを 1 回起動して移行を走らせてから**でないと、S-19 の件数クエリは `Error: in prepare, no such column: is_scratch` を返す（起動前の `SELECT MAX(version) FROM schema_version;` は 2 だった）。起動してから次の 2 つを打ち、両方が真であることを確かめてから S-19 に入ること —— これがこの観測の陽性の対照である。

```bash
sqlite3 "$HOME/Library/Application Support/kamux/app.db" "SELECT MAX(version) FROM schema_version;"
# 期待: 3
sqlite3 "$HOME/Library/Application Support/kamux/app.db" "PRAGMA table_info(sessions);" | grep is_scratch
# 期待: 1 行返る（空なら移行が走っていない。この状態で件数 0 を「増えていない」と読まないこと —— エラーと 0 は別である）
```
