### 3. 🔴 `measure-perf.sh all` を使わないこと。3 つを**この順で別々に**打つ

`all` は `startup` → `memory` → `idle-cpu` の順に走るが、**`startup` は先頭で `pkill -x kamux` を打ってアプリを一度終了させ、新しく起動し直す**（`scripts/measure-perf.sh:214` の逐語）。**したがって、セッション 5 個を開始した状態を作ってから `all` を打つと、その状態は `startup` の時点で壊れ、`memory` と `idle-cpu` は「セッション 0 個のまっさらな起動直後」を測る。** 数字は不当に良く出て、**しかも FAIL にならない**（黙った偽の合格になる）。

正しい順序:

```bash
# (1) 起動時間。アプリは自動で終了・再起動される。セッションの準備はまだ不要
bash scripts/measure-perf.sh startup

# (2) ここで手を動かす: このプロジェクトのセッションを 5 個作成し、5 個とも開始する。
#     同時に見えるのは最大 2 ペインなので、5 個すべてを画面に出すことはできない。
#     起動したかどうかは目視ではなく下の「点 1」のコマンドで数える。
#     他の WebKit アプリは全部終了しておく。スクラッチ端末（Cmd+T）は開かない。
#     そのうえで、出力が止まってから 30 秒以上待つ（契約 §104.3。「操作しない」だけでは
#     足りない。claude が出力し続けている最中に (3) を打つと不当に悪い値が出る）

# (3) メモリとアイドル CPU。実行中はマウス・キーボードに触らない（合計 60 秒強かかる）
bash scripts/measure-perf.sh memory
bash scripts/measure-perf.sh idle-cpu
```

`memory` と `idle-cpu` は**アプリが起動していないと FAIL する**（`kamux が起動していません`）。**しかし (2)（セッション 5 個の作成・起動）が済んだかどうかを、このスクリプトは検出できない。** スクリプトはセッション数を見る経路を 1 本も持たない（`grep -ic 'session\|app\.db\|sqlite' scripts/measure-perf.sh` = 0）。(2) を飛ばして (3) に進んでも FAIL にならず、セッション 0 個の不当に良い数字で PASS してしまう。

**したがって、次の 2 点を自分で確認すること**（自動の検出は無い。点 1 は (3) の 1 本目である `memory` を打つ前に、点 2 は `memory` の出力が出た直後に、それぞれ確認する）:

**点 1 —— kamux が抱えている PTY 子プロセスの本数を数える**（= 実際に起動しているセッションの本数）。

**「5 個すべてが表示されているか」を目で見る形にはしない。** 同時にペインへ載せられるのは最大 2 個で（`paneAssignment` は 2 要素。契約 `00-contracts.md` §10「Zustand ストア形状」の逐語 `paneAssignment: [string | null, string | null];` / `src/store/terminalSlice.ts` の `TerminalSlice` の `paneAssignment: PaneAssignment;` の欄、型の実体は `src/store/paneLogic.ts` の `export type PaneAssignment = [string | null, string | null];`。`Layout` は `src/types/model.ts` の `export type Layout = 'single' | 'split2' | 'split2-v';` の 3 値のみ。**この括弧の引用はいずれも行番号では引かず、逐語を `/usr/bin/grep -nF` で当てる**）、**5 個が同時に見えている状態はこの実装では作れない。** 数えるのは表示ではなく起動である。

```bash
# 🔴 パイプを挟まないこと。`VAR="$(pgrep … | head -n1)"` の $? は
#    パイプ末尾の head のもので、pgrep が該当なしでも 0 を返す（下の「区別」を見よ）。
KAMUX_PIDS="$(pgrep -x kamux)"; PGREP_EXIT=$?
KAMUX_N=$(printf '%s\n' "$KAMUX_PIDS" | awk 'NF{n++} END{print n+0}')
KAMUX_PID=$(printf '%s\n' "$KAMUX_PIDS" | awk 'NF{print; exit}')
echo "pgrep exit=$PGREP_EXIT / 該当 pid 件数=$KAMUX_N / 先頭 pid=[$KAMUX_PID]"
ps -eo ppid=,pid=,comm= | awk -v k="$KAMUX_PID" 'k != "" && $1 == k { print; n++ } END { print "PTY 子 =", n+0 }'
```

- **見る 1 行は 2 つある。順に見ること**:
  1. `echo` の 1 行 —— **`pgrep exit=0 / 該当 pid 件数=1 / 先頭 pid=[<数字>]`**。**`exit=0` かつ `件数=1` でなければ、次の `PTY 子` は読まない**（読んでよい値になっていない）。
  2. `ps | awk` の**最終行** —— **`PTY 子 = 5`**。その手前に子プロセスの行が 5 本並ぶ（`{ print; ... }` があるため、この出力は 1 行ではない。**末尾の 1 行を見ること**）。
- **仮説が偽のときに何が出るか**: セッションを 3 個しか起動していなければ最終行が `PTY 子 = 3` になる。**5 以外なら (2) をやり直す。**
- **3 状態を実測で区別してある**（2026-08-30、ゲート修正 r5 で実施。この機では kamux が起動していなかったため、**「該当あり」の 2 行は kamux ではなく代替のプロセス名で打った**。`exit=` が 2 状態を実際に分けることの確認が目的で、`PTY 子 = 5` そのものは未実測である）:
  - kamux 未起動（`pgrep -x kamux`）→ `pgrep exit=1 / 該当 pid 件数=0 / 先頭 pid=[]` ／ `PTY 子 = 0`（zsh / bash / `zsh -i` の 3 形で同じ）
  - 該当が 1 つ（代替名 `pgrep -x loginwindow`）→ `pgrep exit=0 / 該当 pid 件数=1 / 先頭 pid=[420]`
  - 該当が複数（代替名 `pgrep -x zsh`）→ `pgrep exit=0 / 該当 pid 件数=70 / 先頭 pid=[925]`
- 🔴 **この数が判別できる範囲**: 数えるのは**アプリ全体の PTY 子の本数**であって、内訳ではない。**自分の 5 個に加えて他プロジェクトのセッションも動かしていれば 6 以上になって気づけるが、自分を 3 個しか開始せずに他プロジェクトを 2 個動かしていれば `PTY 子 = 5` を返して通ってしまう。** —— これは人間ゲート 1 回目が落ちた穴そのものである（ai-moderator のセッションの PTY 子 14〜17 本と混ざった）。**したがって、下の事前確認で他プロジェクトのセッションを 1 個も開始しないことが、この観測が成立する前提である。**
- **「0 件」と「コマンドの失敗」の区別**:
  - `PTY 子 = 0` が出ても、`echo` の行が **`exit=1`（= 該当 pid 件数 0）**なら、それは「PTY 子が 0 本」ではなく **kamux 自体が起動していない**（= 観測が不成立）である。**`exit=` を見ずに `PTY 子 = 0` を読まないこと。**
  - 🔴 **この `exit=` が `pgrep` 自身の終了コードであるのは、`KAMUX_PIDS="$(pgrep -x kamux)"` にパイプが無いからである。** ⚠️ **`$(pgrep -x kamux | head -n1)` の形へ戻さないこと** —— その `$?` は `head` のもので、**該当なしでも `0` を返す**（zsh / bash / `zsh -i` の 3 形で実測。2026-08-30 のゲート修正 r5 が是正した欠陥そのもの）。
  - **`件数` が 2 以上**なら `kamux` という名のプロセスが複数ある（典型は dev ビルドとバンドルの同居）。**先頭 1 件しか数えないので `PTY 子` は片方の分しか出ない。** 余分なほうを終了させてから測り直すこと。**`件数=1` を確かめずに `PTY 子` を読むと、ここが黙って過少計上になる。**
- **陽性の対照 1**（この判別が空振りしていないことの確認。**本番を打つ前に 2 状態を打ち、違う値が出ることを見る**）: `V="$(pgrep -x __no_such_proc__)"; echo "exit=$?"` → **`exit=1`**。`V="$(pgrep -x loginwindow)"; echo "exit=$?"` → **`exit=0`**（`loginwindow` は GUI ログイン中の macOS に常駐する。2026-08-30 にこの機で実測。**出なければ別の常駐名に替えてよい。要るのは「必ず該当する名」1 つである**）。**2 つが同じ値なら、この判別は働いていない。**
- **陽性の対照 2**（awk が黙って空振りしていないことの確認）: `ps -eo ppid=,pid=,comm= | awk -v k=1 '$1 == k { n++ } END { print n+0 }'` を打つ。**`launchd` の子が数百本出る**（2026-08-30 の同じ機で 3 度打って `550` / `537` / `531`。**この値は毎回動く。期待値として使わず「数百本出ること」だけを見る**）。ここが `0` なら awk 側が壊れており、`PTY 子 = 0` は信用できない。
- **プロセス名の出所**: `kamux` は `src-tauri/tauri.conf.json` の `productName` である。**探し方（`pgrep -x` に `kamux` を渡し、複数該当なら先頭 1 件を採る）は `scripts/measure-perf.sh` と同一である** —— 逐語 `APP_NAME="${KAMUX_APP_NAME:-kamux}"` と `app_pid() { pgrep -x "$APP_NAME" | head -n1; }`。⚠️ **違うのは 1 点だけ**: 上の形は `$?` で `pgrep` の終了コードを読むためにパイプを外し、先頭 1 件の抽出を `awk` へ移してある。**採る pid は同じである。**
- **WebKit の 3 ヘルパはこの数に混じらない** —— `ppid = 1` だからである（契約 §104.2 の実測 3）。したがって kamux の直接の子は PTY 子である。
- **この数はアプリ全体（全プロジェクトの合計）である。どのプロジェクトのセッションかは判別しない。** プロジェクトの切り分けは次の事前確認で行う。

**点 1 の事前確認（(2) に入る前に 1 回）—— 他プロジェクトが同居していないか**。DB は `~/Library/Application Support/kamux/app.db`（`src-tauri/src/store/mod.rs` の `db_path()`）。

```bash
sqlite3 "$HOME/Library/Application Support/kamux/app.db" \
  "SELECT p.repo_path, COUNT(*) FROM sessions s JOIN projects p ON p.id = s.project_id WHERE s.archived_at IS NULL AND s.is_scratch = 0 GROUP BY p.repo_path;"
```

- **見る 1 行**: `repo_path|件数` が**プロジェクトごとに 1 行**。2026-08-30 の実測（この機の実 DB）は 3 プロジェクトが同居していた:

```
/Users/ooidetatsuya/minedia/ai-moderator|5
/Users/ooidetatsuya/repo/kamux|8
/Users/ooidetatsuya/tmp/repoA|5
```

- 🔴 **この件数は「作成済み・未アーカイブ」であって「稼働中」ではない。** `last_runtime_state` は遷移時にしか書かれず、(1) の `startup` が撃つ `pkill -x`（`scripts/measure-perf.sh:214`）の直後は必ず古い値である。**稼働している本数は点 1（PTY 子）でしか数えられない。この件数を点 1 の代わりに使わないこと。**
- **仮説が偽のときに何が出るか**: 上の実測のように**複数のプロジェクトの行が出るのが通常**であり、**行が 1 本しか無いことは期待していない。** 計測対象以外の行が出たら、そのプロジェクトのセッションは **1 個も開始しないこと** —— 🔴 **点 1 は内訳を持たないので、他プロジェクトを開始したまま自分を 3 個しか開始しなくても `PTY 子 = 5` で通ってしまう。この事前確認は点 1 の補助ではなく、点 1 が成立するための前提である。**
- **「0 件」と「コマンドの失敗」の区別**: DB が無ければ `sqlite3` は `Error: unable to open database "…": unable to open database file` を出して**終了コード 1** を返す（実測）。`is_scratch` 列が無ければ `Error: in prepare, no such column: is_scratch` を返す（= アプリを 1 度も起動しておらず schema_version が 2 のまま。下の「S-19 の前提確認」と同じ状態）。**どちらも「該当 0 件」ではない。空出力と `Error:` を読み違えないこと。**

**点 2 —— 参考値 1 と参考値 2 の突き合わせ（補助。単独では前提の証拠にしない）**

`memory` を実行したら、その出力の `INFO  参考値 1: kamux ツリー（PTY 込み…）` と `INFO  参考値 2: kamux ツリー − PTY 子孫（同上）` の 2 行を見比べる。PTY 子孫（`claude` / `nvim` / シェル）が 1 本でも居れば、その分だけ参考値 1 は参考値 2 より**厳密に大きい**値になる（`descendants` / `non_pty_pids` の実装上、PTY 子孫が 0 本なら 2 つの値は完全に一致する。合成 ps テーブルでの検証結果は post-approval-fix-report.md 参照）。**この 2 つの値が一致していれば、PTY 子孫が 1 本も居らず (2) が効いていない。** その場合は (2) からやり直すこと。

🔴 **点 2 は「PTY 子孫が 1 本以上あること」しか示さない。プロジェクトも個数も判別しない。** したがって **点 2 だけを (2) が済んだ証拠にしてはならない。個数は必ず点 1 で数えること。** —— 人間ゲート 1 回目は点 2 だけを見て「参考値 1 ≠ 参考値 2 で 5 セッション有効」と記録したが、同じ回の記録に「同一アプリ内で他プロジェクト（ai-moderator）のセッションが稼働し PTY 子 14〜17 本」と書かれている。**不一致は他プロジェクトの 1 本でも成立する。**

## 計測条件の数え方（契約 §104 の正典。別の数え方をしないこと）

- メモリは **4 プロセスの RSS の総和**（kamux 本体 + `com.apple.WebKit.WebContent` + `com.apple.WebKit.GPU` + `com.apple.WebKit.Networking`）である（契約 §104.2）。
- **PTY 子孫**（`claude` / `nvim` / シェルとその子孫）は上の総和に**含めない**。ただし子孫を含めた合計値も**参考値として必ず併記する**（契約 §104.2）。
- 対応づけは**起動時刻**で行う。**`ppid` では辿れない**（WebKit ヘルパは `ppid = 1` が既定である）（契約 §104.2 / 実測 3）。
- アイドル CPU は **60 秒平均 < 1.0% かつ最大サンプル < 5.0%**。測り方は `top -l 61 -s 1`、**1 ブロック目を捨てて 2〜61 ブロック目を使う**（契約 §104.3）。

## 再現手順

**🔴 `all` は使わない**（上の「実施者へ」の 3 を参照）。`KAMUX_APP_PATH` を設定したうえで、3 つを別々に打つ:

**S-21 の PTY 残留確認**（コマンドと期待は第1部 §1.5 の 名詞 / 操作 / 観測 の表の `S-21` の行の逐語）:

🔴 **`pgrep -fl 'kamux'` は使わない。** `-f` は argv 全体に当たるので、**実施者がこのリポジトリのディレクトリで端末を開いていれば、その端末自身が該当する。** 2026-08-30 にこの機で実測すると、**kamux が未起動（`pgrep -x kamux` は `exit=1`）の状態で `pgrep -fl 'kamux'` は 14 行返し、その中身は打った本人のシェルだった**（argv に `/Users/ooidetatsuya/repo/kamux` を含むため）。**この件数は同時に何本の端末が走っているかの関数であって、PTY 残留とは無関係である。**

🔴 **前後 2 点で測る。`Cmd+Q` の後だけを見てはならない。** `Cmd+Q` の後は kamux 本体が消えているので `pgrep -x kamux` は空を返し、`k` が空文字になる。**すると `awk` は残骸の有無に関わらず `PTY 子 = 0` を出す**（2026-08-30 実測。`k=""` ではどの数値 `ppid` にも一致しない）。**それは「片付いた」ではなく「測っていない」であり、両方の枝で同じ値が出る = 判別力 0 の観測になる。**

```bash
# --- Cmd+Q を押す「前」に、同じ端末で 2 つとも打つ ---
KPID="$(pgrep -x kamux)"; echo "pgrep exit=$? pid=[$KPID]"
# 見る 1 行: exit=0 かつ pid が 1 個。そうでなければ以降は読まない（読んでよい値になっていない）
ps -eo ppid=,pid=,comm= | awk -v k="$KPID" 'k != "" && $1 == k { print; n++ } END { print "PTY 子 =", n+0 }'
# 見る 1 行（最終行）: PTY 子 = N
# 🔴 N >= 1 であること。N = 0 なら観測不成立で、このまま Cmd+Q を押しても何も測れない

# --- ここで Cmd+Q を押す。KPID は同じ端末に残っているので取り直さない ---

ps -eo ppid=,pid=,comm= | awk -v k="$KPID" 'k != "" && $1 == k { print; n++ } END { print "PTY 子 =", n+0 }'
# 見る 1 行（最終行）: PTY 子 = 0
```

**規則 N の 3 欄**（契約 §158.4）: **① 判別したい形** = 「`Cmd+Q` で PTY 子が片付いた」/「残骸が残った」/「そもそも `Cmd+Q` 前に PTY 子が 0 本だった（観測不成立）」の 3 形。**② 実施者が観測を取る時点** = `Cmd+Q` の**直前**と**直後**。**③ その時点の値の集合と陽性の対照** = `PTY 子` は **`{N, 0}` の 2 値**（`N ≥ 1`）。**陽性の対照は `Cmd+Q` 前の測定そのものである** —— それが `N ≥ 1` を示さないかぎり、後の `0` は「片付いた」の証拠にならない。
